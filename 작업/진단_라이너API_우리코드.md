# 원문을 못 찾는 원인 진단 — 라이너 API vs 우리 코드 (2026-11-14)

질문: 우리 프롬프트·파이썬 문제인가, 라이너 API 성능이 낮은가, API는 좋은데 우리가 잘못 쓰는가?
방법: 단계별로 떼어 실험(실험 스크립트는 세션 임시 폴더 diag.py·diag2.py, 결과 숫자는 아래).

## 1. 라이너 웹 검색 — 성능은 충분. 단, 웹에 원문이 없으면 어느 검색엔진도 못 찾음
정답 원문 위치를 아는 15건(해외 7·국내 8):

| 검색어 | 정답 원문이 20위 안에 | 5위 안에 |
|---|---|---|
| 기사 문장 그대로 | 10/15 | 5/15 |
| 원문 제목을 정확히 알 때 | 13/15 | 13/15 |
| 우리 코드가 실제로 낸 검색어(5~7개) | **15/15** | — |

- 원문 제목을 알면 라이너 검색은 거의 다 1~2위로 찾는다 → 검색 엔진 자체는 문제가 아님.
- 우리 검색어 만들기도 이 15건에서는 모두 원문에 닿았다(주의: 우리가 결국 찾은 건 위주라 유리한 표본).
- 못 찾은 국내 6건을 외부 검색(일반 웹 검색)으로도 찾아봄 → **5건은 외부 검색도 기사만 나오고 원문이 안 나옴**(심평원 건선, 오피넷 유가, 갤럽 주간 결과, 한전 송전선로, 경찰청 살인 통계). 저PBR 151곳은 거래소 KIND 명단 화면. → 이 실패는 라이너만의 한계가 아니라 '원문이 웹에 문서로 없거나 DB 화면 안에 있음'.
- 정부 게시판 보도자료 본문·첨부(HWP)는 검색 색인이 약함 → 정책브리핑 자체 검색·첨부 읽기로 보완(11/14 넣음).

## 2. 라이너 모델(문장 분해) — 정확함
무작위 60건 중 판단 가능한 약 50건: 기관·숫자·영어 검색어 거의 정확. 틀린 것은 바뀐 누리집 주소 3건(기후부 me.go.kr→mcee.go.kr, 데이터처 kostat.go.kr→mods.go.kr)뿐. → 모델은 병목이 아님.

## 3. 라이너 기능을 덜 쓴 것 — 있음
| 기능 | 시험 결과 | 판단 |
|---|---|---|
| **Scholar 검색**(`/tools/search/scholar`) | 영어 검색어로 쓰촨대 논문 1위(전문 PDF 링크). 한국어 검색어는 엉뚱 | **써야 함**(논문: 지금은 PubMed 초록만) |
| Search Agent(`/agents/search`) | 원문을 상위 추천에 올린 건 15건 중 3건(해외 3), 국내 8건은 모두 기사·SNS가 1위. 약 9초 | 원문 찾기 대체는 못 함. 해외 보조 후보 정도 |
| `max_results` 20, `country_code` | 안 씀(기본 10) | 큰 차이 없을 것(우리 검색어로 15/15) |
| 분야별 검색(search_finance 등) | MCP 전용(OAuth) — REST 로 직접 못 씀 | 보류 |

## 4. 우리 코드 — 실패의 상당수는 여기
- 원문 '읽기' 부족(11/14 이전): 게시물 첨부(HWP·HWPX·PDF·엑셀), DART 공시, 접속 차단 누리집, 논문 — 고침 → 무작위 원문 확인 7→11건.
- **흔들림**: 같은 원문을 받아 놓고도 실행마다 고르는 문서·숫자가 달라져 잃음(IEA #30, FEC #18, BLS #15, 청년 은둔 #19). 후보 순위·판정 단계 문제.
- **오판(남은 것)**: 갤럽 표본수 '497+505=1002'를 6월 보고서로 '기사가 계산'(다른 달·의미 없는 계산), 빈곤 기준 '중위소득 50%' 정의 문장을 근거로 댐.
- 숫자 표기 빈틈: '9천151억' 읽기 버그, 백만원 단위(공시) — 고침.

## 결론
라이너 API 성능은 충분하다(검색은 제목만 알면 1~2위, 모델 분해 정확). 원문을 못 찾는 이유는
① 원문이 웹에 문서로 없음(어느 검색엔진도 못 찾음) ② 우리 코드가 원문을 '읽는' 길이 부족했음(고치는 중) ③ 후보 고르기·판정이 흔들림(우리 코드) ④ Scholar 검색 같은 맞는 라이너 기능을 안 씀.
