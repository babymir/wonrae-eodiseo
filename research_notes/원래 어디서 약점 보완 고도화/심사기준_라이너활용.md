# 심사기준 대응과 라이너 API 활용 극대화 (.EXE-THON 2026, 「원래 어디서?」)

조사일: 2026-11-12. [확인]은 출처에서 직접 확인한 사실이고, [추론]은 출처를 바탕으로 우리가 해석한 내용이다.

## 1. 공식 심사기준·규칙: 정확히 무엇을 보나

### Takeaway
심사표는 네 항목이다. 문제 정의 30은 '본인 경험에서 나온 구체적 병목, 누가·언제·얼마나 아픈지'를, 완성도 30은 '실제로 돌아가고 데모에서 문제를 푸는 모습'을 본다. 라이너 API 20은 '핵심 기능에 Model·Search를 적절히 썼는지'를, 확장성 20은 '다른 조직·직무로 퍼질 수 있는지와 시간·비용 절감을 잴 수 있는지'를 본다. 공고문은 "동작하는 에이전트를 보여주면 유리하다"고 적고 있다.

### Cited Findings
- [확인] 심사 항목과 내용: 문제 정의 30%(본인 경험에서 나온 구체적 병목, who/when/how much pain), 완성도 30%(에이전트가 실제로 동작하고 데모에서 문제를 해결하는 모습), 라이너 API 활용 20%(Liner Model·Search를 핵심 기능에 적절히 사용), 확장성·임팩트 20%(다른 조직·직무로 확장 가능, 시간·비용 절감을 측정 가능) — [대회 페이지](https://contests.liner.com/hackathon/exe-thon-2611/)
- [확인] 결선 진출(8팀)은 제출물로 선발하고, 결선도 같은 네 기준으로 심사한다. 심사위원은 라이너 임원과 외부 전문가이며, 개별 점수와 코멘트는 공개하지 않는다 — [대회 페이지](https://contests.liner.com/hackathon/exe-thon-2611/)
- [확인] 데모 영상은 5분 이하다. 아이디어 설명이 아니라 에이전트가 문제를 해결하는 모습을 보여야 하고, 가상 데이터나 공개 라이선스 데이터만 쓰며 개인정보는 넣지 않는다 — [대회 페이지](https://contests.liner.com/hackathon/exe-thon-2611/)
- [확인] 개발 기간은 11/12~25다. 기존 프로젝트를 고도화했다면 **기존 부분과 새로 만든 부분을 명확히 구분**해야 한다. AI 코딩 도구와 다른 모델·오픈소스를 섞어 써도 된다 — [대회 페이지](https://contests.liner.com/hackathon/exe-thon-2611/)
- [확인] 결선은 12/5(토) 라이너 본사(마포)에서 팀당 10분 데모·발표, 5분 질의다. 발표 형식은 자유이고 세부 안내는 따로 온다. 등록 팀원만 발표할 수 있다 — [대회 페이지](https://contests.liner.com/hackathon/exe-thon-2611/)
- [확인] 필수 요건은 Liner Model API 또는 Liner Search API/MCP 중 하나 이상을 핵심 기능에 쓰는 것이다. Model API는 키 하나로 약 500개 모델(OpenAI·Anthropic·Google 등)을 부를 수 있고, Search API/MCP는 실시간 웹·학술 검색으로 제목·발췌·URL·게시일을 돌려준다 — [대회 페이지](https://contests.liner.com/hackathon/exe-thon-2611/)

### Inferences
- [추론] '라이너 API 실무 적용 범위를 넓힌다'가 대회 목적이다. 그러니 라이너 API 20점은 "라이너가 아니면 안 되는 이유"와 "이 사례를 다른 고객사에도 보여줄 수 있는지"로 갈릴 가능성이 크다. "공공 통계·보고서 원문 추적"은 라이너가 보도자료로 쓰기 좋은 사례 모양이다.
- [추론] 대상이 과기정통부 장관상이고 NIA가 함께한다. 공공 데이터 신뢰성, 국가데이터처의 오보 검증 계획 같은 공공적 의미를 확장성·임팩트에서 강조하면 맞물린다.
- [추론] 결선 진출은 제출물(코드·영상·기획서)만으로 정한다. 따라서 11/25 영상과 기획서가 사실상 1차 관문이다. 영상 첫 30초 안에 "실제 기사 → 원문 PDF 쪽 → 판정"이 한 번 끝까지 보여야 한다.
- [추론] '기존/신규 구분' 규칙이 있다. 이전에 만든 파이프라인이 있다면 기획서에 "11/12 이전 / 이후" 표를 넣어 감점 소지를 없앤다.

### Gaps
- 심사위원 명단, 결선 발표 세부 형식(인터넷·화면 환경)은 아직 공개되지 않았다(결선 진출 팀에 따로 안내).
- 라이너가 이전에 연 해커톤의 수상작이나 후기는 찾지 못했다(검색 결과 없음). 이번이 첫 공개 해커톤일 가능성이 있다.

## 2. "라이너 API 활용 20점": 무엇을 더 깊게, 더 눈에 띄게 쓸 수 있나

### Takeaway
지금 우리는 웹 검색, router, gateway의 Gemini를 쓴다. 이것은 '검색과 LLM 호출' 수준이다. 라이너 플랫폼에는 우리 문제와 딱 맞는 기능이 더 있다: 도메인 검색 MCP(`search_finance`가 통계기관·중앙은행 자료를 다룸), Premium Data의 economics 표(`knowledge`), Search Agent의 인용 청크(`referenceChunks`), Decisions(판정 확률), Rerank, Scholar 검색. 이 가운데 2~3개를 "판정 근거가 화면에 보이는" 형태로 붙이는 것이 가장 효과가 크다.

### Cited Findings (라이너 API 구성: 공식 문서 기준)
- [확인] 기본 URL은 `https://platform.liner.com/api/v1`이다. Router(Chat Completions·Responses·Messages), Web/Scholar Search, Visualization, Quick Answer / Search Agent / Deep Research / Visual Answer Agent(SSE)가 있다 — [llms.txt](https://liner.com/llms.txt)
- [확인] Router 모델은 `liner-gpt-router`, `liner-claude-router`, `liner-gemini-router`, `liner-mark`(이전 모델)이고, `routing_strategy`는 cost/balanced/quality다. Router는 웹을 검색하지 않으므로 Search API와 함께 쓰라고 안내한다 — [llms.txt](https://liner.com/llms.txt)
- [확인] Router에는 Decisions, Batches, Embeddings, **Rerank** 등 부가 엔드포인트가 있다 — [llms.txt](https://liner.com/llms.txt)
- [확인] Web Search 파라미터는 `query`, `country_code`, `lang`(ko 가능), `date_range`(past_day~past_year), `max_results`(1–20), `include_knowledge`(기본 true)다. 응답은 title/url/hostname/faviconUrl/description/date와 `knowledge`(title, description, sources, dataAsOf, columns, rows 최대 30개)다. Premium Data 카테고리에 **Economics**와 Prices & rates가 있다. 도메인 포함/제외 필터는 문서에 없다(그래서 우리가 쓰는 `site:` 연산자 방식이 실질적인 대안이다) — [Search API 문서](https://liner.com/developers/docs/search-api)
- [확인] 가격은 웹 검색 $1/1,000건(Premium Data 포함 시 $2/1,000) — [llms.txt](https://liner.com/llms.txt), [라이너 블로그(가격)](https://build.liner.com/blog/category/liner-api)
- [확인] MCP 서버는 `https://platform.liner.com/api/v1/mcp`(Streamable HTTP, OAuth 2.1 또는 API 키)다. 도구는 `search_web`, `search_scholar`, `search_legal`, `search_finance`, `search_medical`, `search_business`, `quick_answer_agent`, `search_agent`, `deep_research_agent`이다. 문서는 가장 좁은 도구부터 쓰라고 권한다(출처를 직접 확인해야 하면 search_web/scholar, 인용 종합이 필요하면 search_agent, 넓은 조사에만 deep_research) — [MCP 문서](https://liner.com/developers/docs/mcp)
- [확인] `search_finance`는 "증권 규제기관, 거래소, 중앙은행, 세무기관, **통계기관**" 자료와 경제지표(관세청·중앙은행·통계기관 자료)를 다루고, 한국 DART·KIND도 웹 공개 범위에서 포함한다. 링크와 스니펫을 돌려주며 "출처를 열어 수치를 검증하라"는 용도로 소개된다 — [Finance MCP 문서](https://liner.com/developers/docs/mcp/finance)
- [확인] Scholar Search MCP 소개 문구는 "논문과 그 안의 주장·수치 확인"이다. 다만 FAQ에 따르면 본문은 읽지 않고, 논문 안 근거 검색은 별도 서버인 Liner Scholar MCP(`api.liner.com/v1/mcp`, Liner Scholar 계정 필요)를 쓰라고 안내한다 — [Scholar MCP 문서](https://liner.com/developers/docs/mcp/scholar)
- [확인] Search Agent API(`/agents/search`)에는 `mode: general|scholar`, `lang`이 있다. SSE 이벤트 `data-search-references`, `data-search-chunks`가 오고, 답변에 [1] 식 인라인 인용과 `referenceChunks`(num, content, sourceTitle, sourceUrl)가 붙는다. 2026년 10월 실측 지연은 p50 약 30초, p90 약 45초다. 도메인 필터는 없다 — [Search Agent 문서](https://liner.com/developers/docs/search-agent-api)
- [확인] Decisions(`/decisions`)는 생성 텍스트 대신 **확률**을 돌려준다. 질문 유형은 `noul`(예/아니오 확률), `choice`(선택지별 확률과 confidence), `score`다. 문서는 "confidence가 낮은 답은 사람에게 넘기라"고 권한다. 예시 모델은 `typesafe/jev-1.13`이고, 입력 토큰에만 과금한다 — [Decisions 문서](https://liner.com/developers/docs/liner-model-api-decisions)
- [확인] Rerank(`/rerank`)는 query와 documents(최대 2,048개)를 넣으면 relevance_score 순으로 돌려준다. 예시 모델은 `cohere/rerank-v3.5`이고 동시 요청은 5개까지다. 한국어 지원은 문서에 없다 — [Rerank 문서](https://liner.com/developers/docs/liner-model-api-rerank)
- [확인] 라이너가 내세우는 가치는 "문장마다 출처 인용, 인용 문장·미리보기 제공", "출처 신뢰도 랭커", SimpleQA 95.3점이다(2025-09) — [라이너 뉴스(trust in search ai)](https://liner.com/ko/news/trust-in-search-ai)
- [확인] 2026-09 연합뉴스 인터뷰에서 CEO 김진우는 "사람이 아닌 AI 에이전트를 위한 구글이 되는 게 라이너의 목표"라고 말했다. 자체 랭커가 5억여 건의 학술논문·검증 웹 출처를 바탕으로 출처 신뢰도와 **인용 맥락**을 판별하며, 논문·심층 보고서 같은 버티컬 검색에 집중한다 — [라이너 뉴스(연합 인터뷰)](https://liner.com/ko/news/liner-interview-yna)
- [확인] 라이너 API 블로그(2026)의 글: 가격 비교(Exa·Brave·Tavily·Perplexity 대비, 7/30), Tavily 대안 Deep Research 비교(8/21), Liner Actions MCP 도구 탐색(8/6) — [build.liner.com 블로그](https://build.liner.com/blog/category/liner-api)

### Inferences (적용 아이디어: 우선순위 순)
1. [추론] **"라이너 인용 UI"를 닮은 근거 화면.** 라이너 브랜드의 핵심은 "문장마다 출처, 인용 문장 미리보기"다. 우리 결과 화면을 '기사 문장 ↔ 원문 PDF p.N의 문장(하이라이트) ↔ 판정 배지 ↔ 출처 URL과 favicon'으로 구성하면, 심사위원(라이너 임원)이 자기 제품의 철학이 확장된 모습으로 읽는다. "라이너가 AI 답변에 해 온 일을 언론 기사에 한다"는 한 문장 포지셔닝도 가능하다. 라이너는 원래 하이라이터 회사이므로, 원문 문장에 형광펜 표시를 하는 것은 상징성도 있다.
2. [추론] **`search_finance` / MCP를 병렬 후보원으로 추가.** 문서가 통계기관·중앙은행 자료를 대상이라고 명시한다. 그러니 "국가데이터처·한국은행 수치" 기사에서 기존 `site:` 검색과 결과를 합치고, 어느 경로가 원문을 찾았는지 로그로 보여줄 수 있다. MCP로 붙이면 "Search API/MCP 둘 다 사용"으로 필수요건 표현도 강해진다. (단, 한국 통계기관 커버리지는 직접 시험해 봐야 한다.)
3. [추론] **Premium Data `knowledge`(Economics)를 '통계표 인용' 판정의 근거로.** 지금 5건을 '통계표·원자료 인용'으로 분류했다. 이 경우 `include_knowledge:true` 응답에 지표 표(dataAsOf, rows)가 있으면 "보고서 PDF가 아니라 지표 DB 값과 대조"라는 추가 근거를 보여줄 수 있다. 국내 지표가 얼마나 들어 있는지는 확인이 필요하다.
4. [추론] **Decisions로 판정 확률(신뢰도) 표시와 사람 확인 요청.** 6종 판정을 `choice` 질문으로 돌리면 선택지별 확률과 confidence를 얻는다. confidence가 낮으면 "사람 확인 필요"로 넘기는데, 이는 문서가 권장하는 패턴 그대로다. 그러면 '2건 판정 불가'를 약점이 아니라 설계된 안전장치로 보여줄 수 있다. 다만 decision 모델의 한국어 성능은 미검증이므로, 기존 router 판정과 나란히 보조 지표로 쓰는 것이 안전하다.
5. [추론] **Rerank로 '보고서 선택 오류' 보완.** 후보 보고서(검색 결과 제목·스니펫, 또는 PDF 쪽 텍스트)를 기사 문장 기준으로 rerank해 상위 N개만 PDF를 읽게 한다. 정확도와 속도(34초)를 함께 개선할 여지가 있고, 라이너 엔드포인트 사용 폭도 넓어진다. 한국어 성능은 직접 측정해야 한다.
6. [추론] **Search Agent(`referenceChunks`)를 '원출처 미확인' 경우의 대체 경로로.** 3개 기관 밖의 기사라면 search_agent의 인용 청크로 "가장 그럴듯한 1차 출처 후보"를 제시하고, '원출처 미확인' 대신 '후보 제시(검증 전)'로 등급을 나눈다. p50 30초라 기본 경로가 아닌 대체 경로로만 쓴다.
7. [추론] **Router `routing_strategy` 사용과 비용표.** 문장 분해는 cost, 최종 판정은 quality처럼 단계마다 다르게 주고, 건당 비용(usage.cost)과 시간을 표로 보여준다. 이는 확장성 항목의 '시간·비용 절감 측정'과 바로 이어진다.
8. [추론] 발표에서 **"라이너 API 사용 지도" 한 장**을 보여준다. 단계마다(문장 분해 → 후보 검색 → 후보 정렬 → PDF 읽기 → 판정 → 신뢰도) 어떤 라이너 엔드포인트를 쓰는지와 호출 수·비용을 적는다. 심사위원이 20점을 바로 매길 수 있게 하기 위해서다.
- [추론] Deep Research Agent는 느리고(다단계) 비싸므로(일본어 페이지 기준 $200/1,000건, 미검증) 핵심 경로에는 맞지 않는다. 시연에서는 "왜 Deep Research 대신 좁은 도구를 조합했는지"를 말할 근거로 쓴다. 이는 문서 권고("가장 좁은 도구부터")와 일치한다.

### Gaps
- gateway 모델에 PDF 파일을 직접 넣는 기능은 공식 문서 요약(llms.txt)에 명시되어 있지 않았다(이미지 입력만 언급). 우리 구현에서 실제로 동작하는 것은 내부에서 확인한 사실이므로, 발표에서는 "라이너 gateway로 Gemini에 PDF 직접 입력"을 우리 실측으로 말한다. 공식 지원 범위는 [llms-full.txt](https://liner.com/llms-full.txt)에서 다시 확인해야 한다.
- `search_finance`·Premium Data의 **한국 통계(국가데이터처·KOSIS·한국은행)** 커버리지는 문서에 구체적으로 없다. 직접 시험해야 한다.

- 라이너가 해커톤 심사에서 'API 활용'을 어떻게 채점하는지 밝힌 글은 찾지 못했다.

## 3. 해커톤 우승작의 공통점과 심사위원이 감점하는 것

### Takeaway
여러 출처(대부분 해커톤 플랫폼 블로그, 즉 의견)가 같은 말을 한다. "특정 사용자의 특정 문제", "AI는 배율기(multiplier)이지 제품 전체가 아님", "처음 한 번에 끝까지 돌아가는 데모", "정량 증거(정확도·비용·지연)"다. 감점 요인은 범용 챗봇, 행동으로 이어지지 않는 대시보드, 데모 실패, 그리고 실제 동작보다 화려한 영상이다.

### Cited Findings
- [확인·의견] 우승 아이디어의 공통점: 특정 사용자의 특정 문제를 풀고, AI는 배율기이며, 데모가 첫 시도에 동작한다. 감점 요인('레드 플래그'): "AI chatbot for X", 과설계, 또 하나의 메모 앱, "데이터만 보여주는 대시보드(행동으로 이어지지 않음)". ML 프로젝트는 정확도를 백테스트 등으로 보여주라고 한다 — [reskilll 블로그](https://blogs.reskilll.com/hackathon-ideas-that-won-2026-judges-actually-pick-examples/)
- [확인·의견] 수작업 워크플로를 대체하는 에이전트(끝까지 동작하는 데모 + 절약한 시간)가 대표적인 우승 패턴이다 — [reskilll 블로그](https://blogs.reskilll.com/hackathon-ideas-that-won-2026-judges-actually-pick-examples/)
- [확인·의견] 에이전트 평가 지표로 작업 완료율, 도구 사용 정확도, 실행당 비용, 지연, 환각률을 제시한다. "심사위원은 데모뿐 아니라 trace 로그를 봐야 한다", "가장 매끈한 데모가 실제 동작 여부와 상관없이 이기는" 것을 문제로 지적한다 — [AngelHack 블로그](https://angelhack.com/blog/ai-agent-hackathon/)
- [확인·의견] 2026년 심사위원은 단순 챗봇을 넘는 프로젝트를 찾고, 데모에서 에이전트의 추론 과정을 보이게 하라고 조언한다(검색 결과 요약 기준). 백업 데모 영상을 준비하고, 메인 브랜치를 데모 가능한 상태로 유지하라는 조언도 있다 — [reskilll 등 검색 결과](https://blogs.reskilll.com/how-to-win-a-hackathon-15-tips-from-92000-team-registrations/), [Masai](https://www.masaischool.com/blog/how-to-win-an-ai-hackathon-in-2026-full-guide/)
- [확인·의견] 심사위원을 사용자 자리에 앉혀 무엇이 일어나는지 따라가게 하라(JetBrains 심사 후기, 검색 요약 기준이며 본문은 403으로 못 읽음). 문제 30% / 해법 70% 시간 배분은 경험칙이다 — [JetBrains 블로그](https://blog.jetbrains.com/ai/2026/06/how-to-win-a-hackathon-notes-from-the-judging-table/), [AngelHack](https://angelhack.com/blog/ai-agent-hackathon/)

### Inferences
- [추론] 우리 도구는 "기자·PM·정책 담당자가 기사 속 수치의 원문을 찾느라 쓰던 시간"을 대체하는 워크플로형 에이전트다. 이는 우승 패턴 1번과 맞는다. 다만 "판정만 보여주는 대시보드"로 보이면 감점 패턴에 걸린다. 그래서 판정 뒤 **행동**을 보여줘야 한다: 원문 문장 복사, 정정 요청 초안, 보고서 인용문 자동 작성 등.
- [추론] 평가표는 "정확도(쪽까지 맞음), 분류 정확, 놓침, 판정 불가, 건당 시간·비용"의 다섯 칸으로 만들면 AngelHack이 말한 에이전트 지표 체계와 일치한다.

### Gaps
- 한국 AI 에이전트 해커톤(2024–2026) 수상작의 데모·발표 구성을 정리한 1차 자료는 이번 조사에서 확보하지 못했다(관련 없는 해커톤 후기만 검색됨).

**완성도(30) 구성**
- [추론] 평가표를 정직하게 낸다: 30건 중 쪽까지 정확 15, 통계표 인용 정확 분류 5, 놓침 8, 판정 불가 2, 평균 34초. 거기에 "놓침 8건의 원인 분류(보고서 선택 오류 n건, PDF 판독 n건…)"와 "고도화 후 재측정"을 덧붙이면 개선 루프가 보인다.
- [추론] 평가 세트를 자체 파이프라인으로 만든 약점은 이렇게 보완한다. 사람이 처음부터 고른 새 기사 10~20건(파이프라인을 거치지 않은 홀드아웃)을 별도로 측정한다. 선정 기준(기간, 언론사, 무작위 추출)을 기획서에 적는다.
- [추론] 시연 안정성: ① 검증된 예시 3건은 캐시나 녹화로 준비한다. ② 라이브 1건은 새 기사로 돌린다. ③ 네트워크·API 실패 시 "저장된 실행 기록 재생" 모드로 넘긴다. ④ 시간 초과나 낮은 confidence는 '사람 확인 필요'로 표시한다. CLI만 있는 상태라면 최소한의 웹 화면(입력창 + 근거 카드)을 만드는 것이 완성도 체감에 가장 큰 영향을 줄 것으로 보인다.
- [추론] 34초 대기는 영상에서 단계별 진행 표시(검색 중 → 후보 3개 → p.12 읽는 중)로 채우면 '추론 가시화'로 바뀐다. 사람이 하면 N분 걸리는 일과 나란히 비교한다.

**확장성·임팩트(20) 구성**
- [추론] "기관 1곳 추가 = 설정 몇 줄(site 도메인, 보고서 목록 패턴)"을 실제로 보여준다. 개발 기간 중 4~5번째 기관을 추가하고, 추가에 걸린 시간을 숫자로 제시하면 강력하다.

- [추론] 라이너 관점의 임팩트: CEO가 말한 "AI 에이전트를 위한 검색"과 "인용 맥락 판별"의 실사용 사례가 된다. 기사와 원문 사이의 인용 맥락을 검증하는 것이 라이너 랭커의 철학과 같은 방향이라는 점을 짚는다.
