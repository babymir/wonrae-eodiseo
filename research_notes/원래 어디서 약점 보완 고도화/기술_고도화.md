# 「원래 어디서?」 추적 에이전트 기술 고도화 (정확도·속도·견고성), 2026-11 기준

> 표기: **[확인]** = 출처로 확인한 사실, **[추론]** = 출처를 근거로 내린 판단(검증 안 됨). 난이도 하·중·상은 혼자 개발할 때 12일(~11/25) 안에 끝낼 수 있는지를 기준으로 매겼다. 기대효과는 관찰된 실패 (a)~(e)에 비추어 매겼다.
> 조사 한계: 도구 호출 약 15회 안에서 조사했다. 블로그 벤치마크는 대부분 동료 검토를 거치지 않았으므로 방향만 참고한다.

## 1. 후보 문서 선택: 기사에 나온 보고서 제목을 후보와 맞추기, 기관에 상관없이 찾기

### Takeaway
기사에 보고서 제목이 나오면 "LLM이 고르기" 전에 **결정적(규칙) 점수**(제목 퍼지 매칭 + 기준시점/발행일 일치 + 기관 도메인)로 먼저 거르고, LLM은 상위 2~3개 중에서만 고르게 하는 2단계 구조가 실패 (a)에 가장 직접 효과가 있다. LLM 재순위기는 어휘가 겹치는 쪽에 끌리는 경향이 보고되어 있어 단독으로 믿으면 안 된다.

### Cited Findings
- rapidfuzz `token_set_ratio`는 어순을 무시하고 부분집합 겹침에 점수를 준다. "Apple Inc"와 "Apple Inc (Cupertino, California)"가 100점이 되므로, 한 제목이 다른 제목의 부분집합이면 중요한 차이(예: 연도, '잠정' 여부)가 있어도 100점이 나올 수 있다 — [RapidFuzz 문서](https://rapidfuzz.github.io/RapidFuzz/Usage/fuzz.html)
- LM 재순위기(re-ranker)는 어휘가 겹치는 문서에 속는다. DRUID 데이터셋에서는 BM25 기준선을 넘지 못했고, 정답 라벨보다 BM25 점수와 더 비슷하게 움직였다 — [Language Model Re-rankers are Fooled by Lexical Similarities (arXiv 2502.17036)](https://arxiv.org/pdf/2502.17036)
- 반대로 제로샷 엔티티 링킹(ZESHEL)에서는 BM25 Acc@10 64.99, Qwen3-Reranker-4B 93.57로 LLM 재순위기가 크게 앞섰다. 효과는 데이터셋에 따라 크게 다르다 — [LELA (arXiv 2601.05192)](https://arxiv.org/html/2601.05192)
- LLM으로 엔티티를 맞출 때 쌍마다 따로 판정(match)하면 후보 사이의 전체 일관성을 놓친다. 후보를 한꺼번에 보여 주고 고르게 하는 'select' 방식, 또는 중간 모델이 순위를 매기고 강한 모델이 상위 k개에서 고르는 2단계를 제안한다 — [Match, Compare, or Select? (arXiv 2405.16884)](https://arxiv.org/html/2405.16884v3)

### Inferences
- **[추론] 제목 정규화 + 퍼지 점수 (난이도 하, 효과 상)**: 기사의 「」『』 안 제목과 후보 PDF 첫 1~2쪽 텍스트, 파일명, 검색결과 제목을 비교한다. 정규화(공백·괄호·'보고서/결과/자료' 같은 꼬리말 제거, 연도·분기 숫자는 따로 뽑기)를 한 뒤 `fuzz.partial_ratio`와 `token_sort_ratio`를 함께 쓴다. **연도·분기·월이 다르면 점수와 상관없이 감점(또는 탈락)**시키는 규칙을 둔다. `token_set_ratio` 단독 사용은 피한다(부분집합 100점 문제).
- **[추론] 메타데이터 일치 가중치 (하, 중~상)**: 기준시점(예: "2025년 3분기")과 PDF 첫 쪽의 기준시점·발행일, 기사 날짜보다 발행일이 늦지 않은지(기사보다 나중에 나온 보고서는 출처일 수 없음), 기관 도메인 일치를 점수에 넣는다. "기사 날짜 이후 발행" 필터만으로도 개정판·후속판 오선택이 줄 것으로 본다.
- **[추론] BM25 (stdlib으로 50줄 내외 구현 가능, 하~중, 중)**: 기사 문장 핵심어로 후보 문서 페이지마다 BM25를 매겨 "숫자가 나오는 쪽 근처 문맥"을 점수화한다. 한국어는 형태소 분석기 없이 글자 2-gram 토큰으로도 쓸 만하다(검증 안 됨, 자체 30건으로 확인 필요).
- **[추론] LLM은 'select' 방식으로 (하, 중)**: 후보를 하나씩 "맞나요?"라고 묻지 말고, 상위 3개의 제목·발행일·기준시점·숫자 주변 문장을 한 프롬프트에 나란히 놓고 "기사가 인용한 보고서는 몇 번인가, 근거가 되는 제목 단어는 무엇인가"를 JSON으로 고르게 한다. 규칙 점수 1위와 LLM 선택이 다르면 '불확실'로 표시한다.
- **[추론] 기관에 상관없이 찾기 (중, 중)**: 기관별 스크래퍼에 기대지 말고, ① 제목을 큰따옴표로 묶은 정확 검색, ② `filetype:pdf` + 핵심어 + 기준시점, ③ 기관 보도자료 HTML 페이지에서 첨부(.pdf/.hwp/.hwpx) 링크를 뽑는 범용 파서(첨부파일 확장자 + `download`/`fileDown` 같은 URL 패턴)를 차례로 시도한다.

### Gaps
- 한국어 보고서 제목 매칭에 대한 BM25·퍼지·임베딩 비교 연구는 찾지 못했다. 자체 30건에서 실패 5건을 다시 돌려 비교해야 한다.
- 한국어 임베딩 모델(예: bge-m3) 성능은 이번 조사에서 확인하지 않았다(Liner API로 임베딩을 쓸 수 있는지도 확인 필요).

## 2. 숫자가 텍스트로 추출되지 않는 한국 정부 PDF

### Takeaway
글꼴에 ToUnicode 매핑이 없으면 텍스트 레이어에서 숫자를 되살릴 방법이 없고, PyMuPDF 문서도 "OCR이 대안"이라고 못박는다. 쪽 단위로 "숫자가 비었는지"를 감지해 그 쪽만 OCR(macOS Apple Vision 또는 Tesseract kor)하고, 인용 검증은 "텍스트 레이어 또는 OCR 텍스트에 있으면 통과"로 바꾸는 것이 현실적이다.

### Cited Findings
- PyMuPDF FAQ: 글꼴에 Unicode 역변환(/ToUnicode)이 없으면 원래 텍스트는 복구할 수 없고 "OCR이 대안"이다. 이를 프로그램으로 확실히 감지하는 방법은 없지만, U+FFFD(대체 문자)가 많으면 이것이 원인일 가능성이 높다. `get_text("rawdict")`로 글자 코드를 보면 진단할 수 있다 — [PyMuPDF FAQ](https://pymupdf.readthedocs.io/en/latest/faq/)
- PyMuPDF는 Tesseract C++ 코드를 내장하고 있어 `page.get_textpage_ocr()`로 쪽 단위 OCR을 하고 `get_text(textpage=tp)`로 읽는다. 필요한 것은 tessdata 언어 파일(`kor.traineddata`)뿐이다. 이미지에 알파 채널이 있으면 OCR이 실패한다 — [PyMuPDF FAQ](https://pymupdf.readthedocs.io/en/latest/faq/)
- 문제가 한 쪽의 일부 글꼴이나 몇 개 글리프에만 있을 수 있어서, 파일 전체를 한 번 검사하는 방식으로는 잘 안 잡힌다 — [MuPDF 포럼](https://forum.mupdf.com/t/any-idea-what-is-wrong-with-this-pdf/47)
- Firecrawl의 pdf-inspector는 U+FFFD, 단어 사이의 과도한 `$`, 치환 암호 같은 통계 신호를 보고 해당 쪽만 OCR로 돌린다(자동 생성 요약 페이지 기반이라 원 저장소 확인 필요) — [pdf-inspector 설명](https://instagit.com/firecrawl/pdf-inspector/pdf-inspector-encoding-issues-and-ocr-fallback/)
- `ocrmypdf-appleocr` 0.4.2: Apple Vision으로 OCR하는 OCRmyPDF 플러그인. 한국어(`kor`)를 지원하고 `pip install ocrmypdf-appleocr`, `ocrmypdf -l kor --ocr-engine appleocr in.pdf out.pdf`로 쓴다. Python 3.11+, OCRmyPDF 14.2.1+(엔진 지정은 17+). 기본 모드 `livetext`는 비공식 private API를 쓰고, 언어를 `+`로 여러 개 묶을 수 없다. Beta 단계 — [PyPI ocrmypdf-appleocr](https://pypi.org/project/ocrmypdf-appleocr/)
- `ocrmac`: Apple Vision을 쓰는 작은 Python 래퍼로, 이미지(경로나 PIL)를 넣으면 글자·신뢰도·박스를 돌려준다. 'fast' 모드는 지원 언어가 적다 — [ocrmac PyPI](https://pypi.org/project/ocrmac); 지원 언어는 패키지가 아니라 macOS 버전에 따라 정해진다 — [Docling OCR 문서](https://docling-project.github.io/docling/concepts/OCR/)
- PaddleOCR은 `lang="korean"`이면 PP-OCRv5 계열을 쓰고, 2026년 6월 나온 PP-OCRv6은 한국어를 지원하지 않는다(한국어 커뮤니티 문서) — [위키독스 PaddleOCR 3.7.0 실측](https://wikidocs.net/441119)
- 2023년 국내 논문에서는 Tesseract 5.0이 (구버전) PaddleOCR보다 한국어 인식이 나았다. 현재 모델 기준의 한국어 비교는 찾지 못했다 — [koreascience 논문](https://koreascience.or.kr/article/CFKO202333854975639.pdf)
- Docling에서 EasyOCR는 기본 신뢰도 기준 때문에 스캔 PDF 글자의 약 절반을 버렸고, 기준을 0.2로 낮추자 되살아났다(한국어 실측 글). RapidOCR의 언어 선택은 공식 문서상 아직 지원하지 않는다 — [위키독스 Docling 실측](https://wikidocs.net/441143), [Docling OCR 문서](https://docling-project.github.io/docling/concepts/OCR/)
- Gemini는 PDF 각 쪽을 이미지로 처리하고(쪽당 258토큰), PDF에 들어 있는 텍스트를 뽑아 함께 넘긴다 — [Gemini 문서 처리](https://aistudio.google.com/docs/document-processing)

### Inferences
- **[추론] 쪽 단위 "숫자 없음" 감지 (하, 상)**: 쪽마다 ① U+FFFD 비율, ② `rawdict`에서 글자는 있는데 숫자(0-9) 비율이 비정상적으로 낮은지(통계 보고서 쪽인데 숫자 0개, 표 선(drawings)은 많은데 숫자 없음), ③ 텍스트에 "천명", "%", "억원" 같은 단위는 있는데 바로 앞이 비어 있는 패턴(`\s+(천명|%|억원)`)을 본다. 실패 사례 (b)는 ③에 바로 걸릴 가능성이 높다.
- **[추론] OCR은 Apple Vision 우선 (하~중, 상)**: 개발 환경이 macOS라면 `page.get_pixmap(dpi=200~300, alpha=False)`로 렌더링 → `ocrmac`(accurate, 언어 `ko-KR`/`en-US`, 정확한 코드는 잘못된 값을 넣었을 때 나오는 오류 목록으로 확인) → 쪽별 OCR 텍스트를 캐시한다. 설치가 가장 쉬운 대안은 PyMuPDF 내장 Tesseract(`brew install tesseract tesseract-lang`)다. 숫자는 한글보다 OCR 오류가 적어 Tesseract로도 쓸 만할 수 있으나 자체 확인이 필요하다. PaddleOCR·Docling은 설치가 무겁고(PaddlePaddle, torch) 12일 안에 위험이 크다.
- **[추론] 배포 서버가 Linux라면** Apple Vision은 못 쓴다. 이때는 Tesseract(kor) 또는 아래 '쪽 이미지 → Gemini' 경로를 쓴다.
- **[추론] 쪽 이미지를 비전 LLM에 보내기 (하, 상)**: 숫자가 깨진 쪽(또는 후보 쪽 3~5개)만 PNG로 렌더링해 gateway Gemini에 보내고 "이 숫자가 있는 줄을 그대로 옮겨 적고 표라면 행·열 머리글을 함께 적어라"라고 요청한다. 쪽당 258토큰이라 비용이 매우 작다.
- **[추론] 텍스트 레이어가 깨졌을 때의 인용 검증 (중, 상)**: "LLM 인용문이 추출 텍스트에 있어야 통과"하던 규칙을 **"텍스트 레이어 또는 독립 OCR 텍스트 중 하나에 숫자+주변 단어가 있으면 통과"**로 넓힌다. LLM이 쪽 이미지를 읽어 나온 결과를 같은 이미지의 OCR로 교차 확인하는 셈이므로 환각을 막는 장치가 유지된다. 비교할 때는 공백·쉼표를 지우고 숫자 열을 정규화한다. 두 결과가 다르면 '판독 불확실'로 보고하고, 쪽 이미지(근거 캡처)를 사용자에게 보여 준다.
- 대안: `ocrmypdf --skip-text`(문서 전체)보다 쪽 단위 OCR이 빠르다. 다만 텍스트 레이어가 '있지만 숫자만 빠진' 쪽에는 `--force-ocr`나 `--redo-ocr`이 필요하다(옵션 동작은 이번 조사에서 직접 확인하지 않음).

### Gaps
- 현재 버전(PP-OCRv5, Tesseract 5.x, Apple Vision)의 한국어 숫자·표 인식 정확도를 직접 비교한 신뢰할 만한 벤치마크는 찾지 못했다. 실패 사례 PDF 몇 개로 직접 비교해야 한다.
- ocrmac의 한국어 언어 코드는 공식 문서로 확인하지 못했다(BCP 47 `ko-KR`일 것으로 추정).

## 3. 큰 PDF 처리(14MB 넘는 PDF)

### Takeaway
Gemini 자체 한도는 PDF 50MB·1,000쪽이므로 "14MB"는 gateway(Liner) 쪽 제한일 가능성이 크다. 어쨌든 전체를 보내지 말고 PyMuPDF로 **후보 쪽(숫자·핵심어가 맞는 쪽 ±1쪽)만 새 PDF로 잘라 보내거나 쪽 이미지로 보내는 것**이 크기·비용·정확도 모두에 낫다.

### Cited Findings
- Gemini는 PDF를 최대 50MB 또는 1,000쪽까지 받는다. 쪽당 258토큰, PDF 안 텍스트에서 뽑은 토큰은 과금하지 않는다. 3072×3072보다 큰 쪽은 줄이고 768×768보다 작은 쪽은 키운다. 해상도를 낮춰도 비용은 줄지 않고, 높여도 성능이 좋아지지 않는다. 한 쪽만 보낼 때는 프롬프트를 쪽 뒤에 둔다 — [Gemini 문서 처리](https://aistudio.google.com/docs/document-processing)
- File API는 파일당 2GB, 48시간 보관 — [Gemini 파일 입력 방법](https://ai.google.dev/gemini-api/docs/generate-content/file-input-methods)
- PyMuPDF로 쪽 범위 추출: 빈 문서를 만들고 `insert_pdf(src, from_page=..., to_page=...)`(0부터 셈). 쪽들이 글꼴·이미지 같은 자원을 공유해서 잘라도 파일이 클 수 있으므로 `ez_save()` 또는 `save(garbage=4, deflate=True, clean=True)`를 권한다 — [PyMuPDF FAQ](https://pymupdf.readthedocs.io/en/latest/faq/)
- 긴 문서 QA에서는 쪽 검색기(ColPali 등)로 관련 쪽을 먼저 고르고 그 쪽만 멀티모달 LLM에 넘기는 방식(M3DocRAG)이 기본 구조이고, 고정 Top-K 대신 쪽 수를 적응적으로 고르는 후속 연구가 있다 — [M3DocRAG (arXiv 2411.04952)](https://web3.arxiv.org/pdf/2411.04952), [CAPS (ACL 2026)](https://aclanthology.org/2026.acl-long.1117.pdf)

### Inferences
- **[추론] 쪽 고르기 → 잘라 보내기 (하, 상)**: 이미 숫자 변형 정규식과 핵심어 문맥으로 쪽 점수를 매기고 있으므로, 상위 3~5쪽 ±1쪽을 `insert_pdf`로 묶어 `garbage=4, deflate=True`로 저장한다(보통 1MB 안팎이 될 것으로 예상). 텍스트에서 숫자가 안 잡히는 PDF(2번)는 '표가 있는 쪽 + 핵심어 쪽'을 고르거나, 목차에서 장 제목 쪽을 찾는다.
- **[추론] 쪽 번호 어긋남 방지 (하, 중)**: 잘라 보낸 PDF의 쪽 번호는 원본과 다르다. 보낼 때 "1쪽 = 원본 37쪽" 같은 대응표를 프롬프트에 넣거나, 결과를 받은 뒤 코드로 원본 쪽 번호로 바꾼다. 인쇄된 쪽 번호(머리말/꼬리말)와 PDF 쪽 번호가 다른 문제도 같이 처리한다.
- **[추론] 이미지 경로**: 쪽 PNG(150~200dpi)는 쪽당 수백 KB라 크기 제한을 사실상 피할 수 있다. 다만 글자가 작은 표는 해상도를 너무 낮추면 읽기가 어려워질 수 있다(Gemini 문서는 "해상도를 높여도 성능은 좋아지지 않는다"고 했으나, 이는 자동 크기 조정 범위 안의 이야기로 읽힌다).

### Gaps
- Liner gateway의 정확한 업로드 한도와 쪽 이미지 여러 장을 한 요청에 넣을 수 있는지 확인하지 못했다(Liner API 문서 확인 필요).

## 4. 표 추출(단위가 머리글에 있는 표)과 HWP/HWPX

### Takeaway
표 숫자는 "숫자 셀 ↔ 행 머리글 ↔ 열 머리글 ↔ 표 제목·머리글의 단위(천명, %, 억원)"를 묶어야 검증된다. 12일 안에는 PyMuPDF `find_tables()`(이미 설치됨)로 시작하고, 표가 어려운 경우만 OpenDataLoader PDF(로컬 모드, Java 11+)나 쪽 이미지 → LLM을 쓰는 것이 현실적이다. HWP는 `unhwp`/`syhwp` 같은 새 Python 라이브러리로 텍스트를 뽑을 수 있다.

### Cited Findings
- PyMuPDF는 1.23(2023)부터 `Page.find_tables()`를 제공한다. Camelot 쪽 비교 문서에 따르면 PyMuPDF는 선 위치(geometry)만으로 표를 찾아 테두리 없는 표에 약하다 — [Camelot 비교 문서](https://camelot-py.readthedocs.io/en/latest/user/comparison.html)
- 블로그 벤치마크들은 서로 엇갈린다: PyMuPDF 표 검출 93% vs Camelot 87% vs pdfplumber 79%(검출 기준) — [dev.to 벤치마크](https://dev.to/vtempest/pdf-gec); 금융 PDF 50개에서는 pdfplumber 86%, Camelot 75%, PyMuPDF 65% — [bswen 블로그](https://docs.bswen.com/blog/2026-03-16-pdfplumber-vs-pymupdf); 단일 PDF 셀 단위 비교에서 행 정확도 pdfplumber 51.1%, Camelot stream 88.9%, PyMuPDF 82.2% — [dev.to 셀 비교](https://dev.to/felipe_anyformat/extract-tables-from-a-pdf-2d0h). 모두 동료 검토가 없는 개인 시험이다.
- OpenDataLoader PDF(한컴): `pip install -U opendataloader-pdf`, Java 11+ 와 Python 3.11+ 필요, Apache-2.0(2.0부터). 기본(로컬, 규칙 기반) 모드는 0.015초/쪽, 표 점수 0.489. hybrid 모드(AI 백엔드)는 표 0.928, 전체 0.907, 0.463초/쪽(M4, 자체 벤치마크). 출력 JSON 요소마다 쪽 번호(1부터)와 bounding box(PDF pt)가 있다. 스캔 PDF는 hybrid + `--force-ocr`, 한국어는 `--ocr-lang "ko,en"`, OCR 엔진으로 EasyOCR(기본)·RapidOCR·Tesseract·Apple Vision을 고를 수 있다 — [OpenDataLoader GitHub](https://github.com/opendataloader-project/opendataloader-pdf)
- 한컴은 v2.0(2026-03-13 발표)이 오픈소스 파서 중 읽기 순서·표 추출·제목 추론에서 1위라고 발표했다. 회사 자체 시험이다 — [PR Newswire 보도자료](https://www.streetinsider.com/PRNewswire/Hancom+Tops+Open-Source+PDF+Benchmarks+with+OpenDataLoader+PDF+v2.0/26157001.html)
- LLM 표 QA 오류 분석: 머리글을 데이터 행으로 착각해 한 행씩 밀리는 오류(TABVERSE), 여러 줄 머리글에서 열 이름 인식 오류(TabDSR), 단위·척도 불일치가 주요 왜곡 유형으로 꼽힌다 — [TABVERSE (arXiv 2606.09578)](https://arxiv.org/pdf/2606.09578), [표 왜곡 견고성 (arXiv 2601.05009)](https://arxiv.org/html/2601.05009v1)
- 금융 표 QA 데이터셋 TAT-QA는 답마다 척도(scale: thousand, million, billion, percent)를 따로 예측하게 해서, 표의 단위 표기를 답과 분리해 다룬다 — [TAT-QA (arXiv 2105.07624)](https://arxiv.org/abs/2105.07624)
- HWP/HWPX Python 라이브러리: `syhwp`(순수 Python, HWP·HWPX → 텍스트/Markdown/HTML, MIT, 의존성 olefile뿐) — [PyPI syhwp](https://pypi.org/project/syhwp/); `unhwp`(Rust 기반, HWP 5.0·HWPX·HWP 3.x → Markdown/텍스트, macOS 지원) — [PyPI unhwp](https://pypi.org/project/unhwp/0.6.0/); `master-of-hwp`(구역·문단·표 접근) — [PyPI master-of-hwp](https://pypi.org/project/master-of-hwp/0.2.2/); pyhwp(`hwp5txt`)는 AGPL-3.0이라 SaaS에 쓰기 어렵다(syhwp 쪽 설명) — [PyPI syhwp](https://pypi.org/project/syhwp/)

### Inferences
- **[추론] 단위 붙이기 규칙 (중, 상)**: 숫자를 찾은 쪽에서 ① 표 위 2~3줄과 표 첫 행·첫 열에서 `(단위\s*[:：]\s*([^)]+))`, `[천명]`, `(%)`, `(억원)` 패턴을 찾고, ② 숫자가 있는 셀의 열 머리글과 행 머리글을 `find_tables()` 결과(`table.extract()`, `header.names`)에서 가져와 "값=8,671, 단위=천명, 행=전체, 열=2025.10"처럼 묶는다. 기사 수치 "867만1천명"은 단위를 곱해 정수로 바꾼 뒤 비교한다(8,671 × 1,000 = 8,671,000). 이미 있는 숫자 변형 정규식을 "단위 환산 후 비교"로 바꾸는 것이 핵심이다.
- **[추론] 표가 어려우면 LLM에게 쪽 이미지 + "행 머리글/열 머리글/단위/값"을 JSON으로 요구 (하, 중~상)**: 결과 값은 반드시 텍스트 레이어나 OCR에서 다시 찾아 검증한다(2번과 같은 원칙).
- **[추론] OpenDataLoader 로컬 모드 (중, 중)**: Java가 필요하지만 설치는 pip 하나다. 로컬 모드의 표 점수(0.489)는 낮아 단독 사용은 어렵고, JSON의 쪽 번호·bbox가 근거 표시(하이라이트)에 쓸모가 있다. hybrid는 AI 백엔드 서버를 따로 띄워야 해서 12일 안에는 위험하다.
- **[추론] HWP 대응 (하~중, 중)**: 정부 보도자료 첨부가 HWP만 있는 경우, `unhwp` 또는 `syhwp`로 텍스트를 뽑아 같은 숫자 정규식을 돌린다. HWP에는 'PDF 쪽' 개념이 없으므로 결과를 "HWP 문서 n번째 표/문단"으로 보고하고, 같은 보도자료에 PDF가 같이 있으면 PDF를 우선한다. 라이선스는 MIT(syhwp)를 우선한다.

### Gaps
- 한국 통계 PDF(통계청·고용노동부 등)에서 표 추출기를 비교한 자료는 찾지 못했다.
- unhwp·syhwp의 표 추출 품질과 안정성(버전이 매우 새 것)은 확인하지 않았다. 실제 보도자료 HWP 몇 개로 시험해야 한다.

## 5. 판정 신뢰도와 평가 방법

### Takeaway
숫자 주장을 작은 단위(기관·보고서·기준시점·숫자·단위·대상)로 나눠 따로 맞춰 보는 방식이 숫자 팩트체크 정확도를 높인다는 근거가 있다. LLM 판정의 '자신감'은 과대평가되는 경향이 있으므로 근거 일치 규칙과 '판단 보류(abstain)'를 함께 써야 하고, 평가는 쪽 단위 정답 세트로 해야 한다.

### Cited Findings
- QuanTemp: 45개 팩트체크 기관의 실제 숫자 주장 15,514건 데이터셋. 최고 기준선 macro-F1 58.32로 어려운 과제다. 주장을 작은 하위 질문으로 나누는 ClaimDecomp가 검증 정확도를 크게 높였다 — [QuanTemp (arXiv 2403.17169)](https://arxiv.org/pdf/2403.17169)
- QuanTemp++(2025-10)는 원래 QuanTemp의 근거가 시점 누출(주장 이후 자료가 근거로 들어감)과 잡음 문제가 있다며 근거 말뭉치를 다시 구성했다 — [QuanTemp++ (arXiv 2510.22055)](https://arxiv.org/abs/2510.22055)
- LLM 판정자는 실제 정확도보다 더 자신 있게 말하는 경향(과신)이 있다 — [arXiv 2512.22245](https://arxiv.org/pdf/2512.22245v1)
- 자기 일관성(여러 번 물어 같은 답이 나오는지)과 모델 간 합의는 조건부로만 정답과 연관되며, 공유된 편향일 수 있다 — [When LLMs Agree, Are They Right? (arXiv 2607.08065)](https://www.alphaxiv.org/abs/2607.08065.md)
- Cascaded Selective Evaluation: 싼 판정자가 자신 있을 때만 답하고 아니면 강한 모델로 넘기며, 사람과의 일치율이 정한 수준 이상이 되도록 기준을 보정한다 — [Trust or Escalate (arXiv 2407.18370)](https://arxiv.org/html/2407.18370v1)
- 판단 보류의 주된 원인은 근거 모순과 답의 의미 분산이었다(UniCR) — [arXiv 2509.01455](https://arxiv.org/html/2509.01455v1)

### Inferences
- **[추론] 판정을 '규칙으로 확인 가능한 부분'과 'LLM 판단'으로 나누기 (중, 상)**: 숫자·단위 일치(코드), 기준시점 일치(코드), 보고서 제목 일치(코드 점수), 의미 일치(LLM: "같은 대상·같은 지표인가")로 나누고, 코드 확인이 하나라도 실패하면 LLM이 '일치'라고 해도 최종 판정을 '부분 일치/확인 필요'로 낮춘다.
- **[추론] 판단 보류를 정식 결과로 (하, 중)**: "찾음 / 기자 계산 / 찾지 못함" 외에 "후보는 찾았으나 확신 낮음(사람 확인 필요)"을 두고, 조건(규칙 1위 ≠ LLM 선택, 텍스트·OCR 불일치, 표 단위 미확인)을 명시한다. 30건 중 틀린 답을 내는 것보다 보류하는 편이 서비스 신뢰에 낫다.
- **[추론] 자기 일관성은 아껴 쓰기 (하, 하~중)**: 같은 모델에 2~3번 묻는 것은 비용이 2~3배다. 규칙 점수가 애매한 경우(상위 두 후보 점수 차가 작을 때)에만 쓴다.
- **[추론] 평가 세트 만들기 (중, 상)**: 기사 30건을 정답 표(기사 문장, 숫자, 정답 보고서 URL, 정답 PDF 쪽 번호(복수 허용), 결과 유형: 원문 있음/기자 계산/원문 없음)로 만든다. 지표는 ① 문서 정확도, ② 쪽 정확도(정답 쪽 ±0, ±1 따로), ③ 판정 정확도, ④ 보류율과 '보류하지 않은 것 중 정확도', ⑤ 건당 시간·비용. 30건 가운데 5~10건은 둘이 따로 정답을 달아 일치율(간단히 일치 비율, 가능하면 Cohen's kappa)을 본다.
- **[추론] 표본 편향 피하기 (하, 중)**: 지금 30건이 쉬운 기관(통계청 등)에 몰렸을 수 있다. 개발용(튜닝) 20건과 마지막 확인용 10건 이상을 나누고, 확인용은 개발 중에 보지 않는다. 기관·형식(PDF/HWP/스캔)·숫자 유형(비율/인원/금액)별로 고르게 뽑고, 정답이 "원문 없음"인 기사도 넣는다. QuanTemp++가 지적한 시점 누출처럼, 기사 날짜 이후 나온 자료가 정답으로 잡히지 않게 한다.

### Gaps
- 한국어 숫자 주장 검증 데이터셋이나 한국 기사 기반 벤치마크는 이번 조사에서 찾지 못했다.

## 6. 속도와 비용(건당 약 34초)

### Takeaway
가장 큰 효과는 ① 다운로드·텍스트 추출·OCR·LLM 응답을 URL/파일 해시 기준으로 캐시하고, ② 후보 PDF 다운로드와 추출을 병렬로 돌리고, ③ 규칙만으로 확정되면 LLM 단계를 건너뛰는 조기 종료, ④ 전체 PDF 대신 고른 쪽만 보내기다. 모두 난이도 하~중이다.

### Cited Findings
- Gemini는 PDF 쪽당 258토큰이고 PDF 안 텍스트 토큰은 과금하지 않는다. 그래서 쪽 수를 줄이는 만큼 비용이 거의 비례해서 줄어든다 — [Gemini 문서 처리](https://aistudio.google.com/docs/document-processing)
- File API에 올린 파일은 48시간 보관되어 같은 문서를 여러 번 물을 때 다시 올릴 필요가 없다 — [Gemini 파일 입력 방법](https://ai.google.dev/gemini-api/docs/generate-content/file-input-methods)
- OpenDataLoader 로컬 모드는 쪽당 0.015초(CPU)로 매우 빠르다(자체 측정) — [OpenDataLoader GitHub](https://github.com/opendataloader-project/opendataloader-pdf)
- 싼 판정자가 먼저 답하고 불확실할 때만 강한 모델로 넘기는 구조가 비용을 줄이면서 품질 기준을 지킬 수 있다 — [Trust or Escalate (arXiv 2407.18370)](https://arxiv.org/html/2407.18370v1)

### Inferences
- **[추론] 캐시 (하, 상)**: `cache/` 폴더에 PDF(URL의 sha1), 쪽별 텍스트·OCR, 검색 결과(질의 문자열 해시), LLM 응답(프롬프트 해시)을 JSON으로 저장한다. 같은 보고서를 인용한 기사가 많고(같은 통계 발표를 여러 언론이 인용), 시연 중 재실행도 빨라진다.
- **[추론] 병렬화 (하, 상)**: `concurrent.futures.ThreadPoolExecutor`(stdlib)로 Liner 검색 질의 여러 개, PDF 다운로드, 첫 쪽 기준시점 확인을 동시에 돌린다. 네트워크 대기가 대부분이라 스레드로 충분하다. API 속도 제한에 맞춰 동시 실행 수를 4~6개로 제한한다.
- **[추론] 조기 종료 (하, 중~상)**: 제목 점수가 높고 + 기준시점이 맞고 + 숫자·단위·핵심어가 같은 쪽에서 정확히 맞으면 LLM 선택 단계를 건너뛰거나 가벼운 모델로 확인만 한다. 첫 쪽 기준시점이 맞지 않는 PDF는 본문을 추출하지 않는다(이미 하고 있다면 다운로드도 Range 요청이나 HEAD로 크기를 먼저 보고 거른다).
- **[추론] 모델 나누기 (하, 중)**: 문장 분해·후보 선택은 빠른 모델, 쪽 이미지 판독과 최종 판정만 강한 모델로 한다. 단계별 소요 시간을 로그로 남겨 34초 중 어디가 큰지 먼저 잰다(측정 없이 최적화하지 않기).
- **[추론] 우선순위 제안 (12일 기준)**: 1) 쪽 단위 숫자 깨짐 감지 + 쪽 이미지 → Gemini + OCR 교차 확인(실패 b·c 해결), 2) 제목·기준시점·발행일 규칙 점수 + LLM select(실패 a), 3) 고른 쪽만 잘라 보내기(c·e), 4) 단위 머리글 연결(d), 5) 캐시·병렬(e), 6) 정답 세트 + 보류 결과 유형(평가). HWP와 OpenDataLoader는 시간이 남으면.

### Gaps
- Liner API의 요금, 속도 제한, 모델별 응답 시간은 이번 조사 범위 밖이라 확인하지 못했다.
- Gemini의 문맥 캐시(context caching) 조건과 할인율은 문서 처리 페이지에 없어 확인하지 못했다(gateway에서 지원하는지도 불명).
