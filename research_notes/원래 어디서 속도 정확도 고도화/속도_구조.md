# 「원래 어디서?」 건당 30~40초 → 수 초로: 속도 구조 조사

> 작성 2026-11-13. 코드는 읽기만 했다(수정 없음). 앞 보고서(`reports/원래 어디서 약점 보완 고도화.md` 29행)에 이미 있는 내용은 다시 쓰지 않았다. 그 내용은 "단계별 시간 로그 먼저, URL·해시 캐시, 검색·다운로드 4~6개 병렬, 규칙으로 확정되면 LLM 건너뛰기, 진행 표시"다. 이 노트는 그 위에 **라이너 API의 구체 설정값, 호출 순서 재배치, 체감 속도**를 더한다.
> 출처 링크가 없는 문장은 모두 코드를 읽고 한 추론이다. "예상 효과"는 재지 않은 값이다.

## 지금 흐름에서 시간이 새는 곳 (코드 확인 결과)

### Takeaway
한 건 처리에 라이너 호출이 **순서대로 최소 6~7번, 많으면 12번 이상** 이어진다. 그런데 모델 호출에는 `reasoning_effort`·`routing_strategy`·`stream`을 하나도 주지 않는다. 그래서 라우터 기본값(추론 medium, balanced)으로 돈다. 웹 서버는 `RUN_LOCK`으로 한 번에 한 건만 처리한다.

### Cited Findings
- 코드상 호출 순서(`도구/원문찾기.py` `run()`)는 다음과 같다. ① 모델 분해 `extract` → ② `search_all`: site 검색 2번과 일반 검색 1번을 **for 문으로 차례로** → ③ 후보가 6개를 넘으면 Rerank(제목) → ④ `load_docs`: 최대 `MAX_DOWNLOAD = 6`개 PDF를 **차례로** 받고 pdftotext → ⑤ Rerank(표지) → ⑥ PDF마다 `rank_hits`(Rerank)와 `choose`(모델)를 최대 2개 PDF까지 → ⑦ 못 찾으면 `read_pdf`(게이트웨이 Gemini, 최대 2번) → `choose` 한 번 더 → ⑧ `check_calculation`(모델) 또는 `cross_check`(Decisions). — 코드: `도구/원문찾기.py` 45~196행, `도구/판정.py`
- `도구/liner_api.py`의 `ask_json`은 body에 `model`과 `messages`만 넣는다. 그래서 `reasoning_effort`·`routing_strategy`·`response_format`·`max_completion_tokens`·`stream`이 모두 기본값이다. JSON은 정규식으로 뽑는다. — 코드: `도구/liner_api.py`
- 라이너 Chat Completions의 `reasoning_effort` 기본값은 **`medium`**이다. 값은 `none, low, medium, high, max`이고, `liner-gemini-router`에서 `none`은 400 오류다. — [Chat Completions 문서](https://liner.com/developers/docs/liner-model-api-chat-completions)
- PDF 다운로드는 파일 단위 캐시가 이미 있다(`download_pdf`에서 `path.exists()`면 다시 받지 않음, `작업/원본PDF/`에 210개). pdftotext 결과·검색 결과·모델 답은 캐시가 없다. — 코드: `도구/PDF도구.py` 37~55행
- 웹 서버는 `ThreadingHTTPServer`지만 `work()`가 `RUN_LOCK`을 잡는다. 진행 상황은 `print`를 가로채 `job["steps"]`에 쌓고, 화면이 그것을 폴링한다. — 코드: `도구/웹서버.py` 30~62행
- 측정된 평균 시간은 3차 34초, 4차 30초, 5차 27초(기존 30건), 새 기사 19건 41초다. — `진행현황.md` 27·32·40·46행

### Inferences
- 단계별 시간 로그가 없어 어느 단계가 가장 큰지는 아직 모른다. 다만 호출 수로 보면 **순차 네트워크 왕복(검색 3, 다운로드 최대 6, Rerank 2~4, 모델 3~5)**이 대부분일 것으로 본다. 게이트웨이 PDF 읽기(⑦)까지 가는 건은 그 한 단계가 10초 이상일 가능성이 높다(재지 않음).
- 그러니 가장 먼저 할 일은 `time.perf_counter()`로 단계별 시간을 결과 JSON에 남기는 것이다(30분 작업). 아래 우선순위는 이 측정으로 다시 확인해야 한다.

### Gaps
- 단계별 실제 시간 분포. 로그가 없어 알 수 없다.
- 라이너 라우터가 어느 하위 모델로 보냈는지(응답 `model` 필드)를 지금까지 기록하지 않아, 어떤 모델이 느렸는지도 알 수 없다.

## 라이너 API에서 속도에 쓸 수 있는 것 (2026-11 문서 기준)

### Takeaway
가장 큰 지렛대는 **`reasoning_effort`를 낮추는 것**(기본 medium → 분해·선택은 `none`/`low`)과 **동시 호출 한도 안에서 병렬화**다. Batch는 24시간 창이라 실시간에는 못 쓴다. 웹 검색은 스트리밍이 없어 병렬화로만 줄일 수 있다.

### Cited Findings
**모델 선택·추론량**
- `liner-gpt-router`의 하위 모델은 싼 것부터 `gpt-6-luna`, `gpt-6.1-terra`, `gpt-6.1-sol`, `gpt-6-astra`이고, 전략과 상관없이 같은 풀에서 고른다. `routing_strategy`는 `cost`, `balanced`(기본), `quality` 중 하나다. — [GPT Router 문서](https://liner.com/developers/docs/llm-gpt-router)
- `reasoning_effort: "none"`이면 `gpt-6-luna`·`gpt-6.1-terra`는 그대로 답한다. 대신 `gpt-6.1-sol`·`gpt-6-astra` 자리에는 `gpt-6-sol`이 답한다. 응답의 `model` 필드에 실제로 답한 모델 이름이 나온다. — [GPT Router 문서](https://liner.com/developers/docs/llm-gpt-router)
- `liner-gemini-router`의 하위 모델은 `gemini-3.5-flash-lite`, `gemini-3.8-flash`, `gemini-4-argon`이고, `reasoning_effort`는 low~max만 받는다(none 없음). — [Gemini Router 문서](https://liner.com/developers/docs/llm-gemini-router)
- 게이트웨이에서 바로 부를 수 있는 작고 빠른 모델과 값(1M 토큰당 입력/출력 USD): `openai/gpt-6-luna` 0.1/0.5, `anthropic/claude-haiku-5.5` 0.1/0.5, `google/gemini-3.5-flash-lite` 0.3/2.5, `google/gemini-3.1-flash-lite` 0.25/1.5, `openai/gpt-5.4-nano` 0.2/1.25. 지금 PDF 읽기에 쓰는 `google/gemini-3.8-flash`는 0.825/4.125다. — [LLM Gateway 문서](https://liner.com/developers/docs/llm-gateway)
- Gemini 공식 문서의 모델별 기본 추론 수준: `gemini-3.8-flash`는 **medium**(low/medium/high 가능), `gemini-3.5-flash-lite`·`gemini-3.1-flash-lite`는 **minimal**이다. low는 "Fewest tokens, lowest latency", minimal은 "Near-off thinking, lowest latency"로 설명한다. — [Gemini thinking 문서](https://aistudio.google.com/docs/thinking)
- 라우터·Liner 모델이 아닌 카탈로그 모델만 파일(PDF)을 받는다(예: `google/gemini-3.8-flash`, `anthropic/claude-opus-5.5`). — [Chat Completions 문서](https://liner.com/developers/docs/liner-model-api-chat-completions)

**구조화 출력·출력 길이**
- `response_format`은 `json_object`와 `json_schema`(`strict`, enum·anyOf 지원)를 받는다. 출력 길이 제한은 `max_completion_tokens`다(`max_tokens` 없음). — [Chat Completions 문서](https://liner.com/developers/docs/liner-model-api-chat-completions)
- OpenAI 지연 최적화 안내: "출력 토큰을 50% 줄이면 지연이 약 50% 줄 수 있다", "프롬프트를 50% 줄여도 1~5%만 좋아진다". 순차 단계를 한 프롬프트로 합쳐 JSON으로 받으라("Make fewer requests")고도 권한다. — [OpenAI Latency optimization](https://developers.openai.com/api/docs/guides/latency-optimization)

**스트리밍**
- `stream: true`면 SSE(`chat.completion.chunk`, 끝은 `data: [DONE]`)로 온다. `stream_options.include_usage`로 사용량도 받는다. 스트림 중 오류는 `[DONE]` 없이 `error` 청크로 온다. — [Chat Completions 문서](https://liner.com/developers/docs/liner-model-api-chat-completions)
- 125초쯤 아무 응답이 없으면 라이너 엣지 프록시가 끊고 HTML 524를 돌려준다. 스트리밍 요청은 15초마다 `: keep-alive`를 보내 이를 피한다. — [Chat Completions 문서](https://liner.com/developers/docs/liner-model-api-chat-completions)
- 웹 검색 API는 "Plain JSON response (no streaming)"다. 문서에 지연 수치는 없고, `(query, country_code, lang, date_range, include_knowledge)`로 캐시하라고 권한다. — [Search API 문서](https://liner.com/developers/docs/search-api)

**프롬프트 캐시**
- 1,024토큰 이상이고 앞부분(prefix)이 같은 요청은 자동으로 캐시된다. 캐시된 토큰은 usage에 나온다. — [Chat Completions 문서](https://liner.com/developers/docs/liner-model-api-chat-completions)
- GPT Router의 캐시는 30분 유지되고 바꿀 수 없다. 캐시 쓰기는 입력 단가보다 비싸다. Claude Router는 `prompt_cache_key`가 있어야 켜진다. — [GPT Router 문서](https://liner.com/developers/docs/llm-gpt-router), [Chat Completions 문서](https://liner.com/developers/docs/liner-model-api-chat-completions)

**PDF 입력**
- `file_data`에는 base64 data URL 말고 **`https://` URL도 넣을 수 있다**. URL은 요청당 20MB 한도에 들어가지 않는다. 저장된 `file_id`는 지원하지 않는다. — [Chat Completions 문서](https://liner.com/developers/docs/liner-model-api-chat-completions)
- Gemini는 PDF 한 쪽을 258토큰으로 계산한다. 쪽 하나만 보낼 때는 프롬프트를 쪽 **뒤에** 두라고 권한다. 반복해서 쓰는 큰 파일은 Files API가 "업로드와 모델 요청을 분리해 지연을 줄인다"고 한다. — [Gemini 문서 처리](https://aistudio.google.com/docs/document-processing). 다만 라이너 게이트웨이는 `file_id`를 지원하지 않아 Files API 방식은 쓸 수 없다([Chat Completions 문서](https://liner.com/developers/docs/liner-model-api-chat-completions)).

**동시 호출·속도 제한**
- 라우터 API(`liner-` 모델)는 초당 100건·분당 1,000건이다. 다른 모델도 같은 한도지만 풀이 따로다. 웹 검색은 초당 한도가 없고 "fair use"를 따른다. **Rerank·임베딩은 계정당 동시 5건**이고, 넘으면 429 `concurrency_limit_exceeded`, `Retry-After: 5`다(과금 안 됨). — [Rate limits 문서](https://liner.com/developers/docs/rate-limits)
- 게이트웨이 페이지에는 "계정당 동시 5건" 문장이 있다. 다만 Chat·임베딩·Rerank를 따로 센다고 적혀 있고, 이 한도가 일반 Chat에도 걸리는지는 Rate limits 문서와 표현이 엇갈린다. Rate limits 문서는 동시 한도 대상을 임베딩·Rerank·음성·이미지로만 든다. — [LLM Gateway 문서](https://liner.com/developers/docs/llm-gateway); [Rate limits 문서](https://liner.com/developers/docs/rate-limits)
- 429를 다룰 때는 응답의 `retryable` 필드와 `Retry-After`(최소 대기)를 보고, 지터를 넣은 지수 백오프를 쓰라고 한다. — [Rate limits 문서](https://liner.com/developers/docs/rate-limits)

**Batch**
- Batch는 `completion_window`가 `24h` 하나뿐이고 `:batch` 모델로만 돈다(예: `anthropic/claude-haiku-5.5:batch` 0.05/0.25). — [Batch 문서](https://liner.com/developers/docs/liner-model-api-batches), [LLM Gateway 문서](https://liner.com/developers/docs/llm-gateway)

### Inferences
- **추론 끄기/낮추기가 가장 싸고 큰 개선이다.** 분해(`extract`)와 후보 고르기(`choose`)는 짧은 JSON을 내는 일이다. `reasoning_effort: "none"` + `routing_strategy: "cost"`(luna/terra로 갈 가능성 높음)면 호출당 수 초가 줄 것으로 본다. 판정이 들어가는 `choose`는 `low`로 두고 평가 30건에서 정확도가 그대로인지 확인한다. 게이트웨이 PDF 읽기도 `reasoning_effort: "low"`를 준다(Gemini 3.8 Flash 기본 medium). 예상 효과는 건당 −5~15초이고 작업은 1시간이다(추론, 재지 않음).
- `response_format: json_schema` + `max_completion_tokens`로 출력을 짧게 묶는다. 정규식 파싱 실패도 함께 사라진다.
- **PDF를 URL로 넘기기**: 기관 PDF 주소를 `file_data`에 그대로 넣는다. 그러면 base64 인코딩과 수 MB 업로드가 없어지고 14MB 한도도 풀린다. 단, 정부 사이트가 라이너 서버의 접근을 막거나 세션·리퍼러를 요구하면 실패할 수 있다. 실패하면 지금 방식으로 되돌아가는 대안 경로를 둔다. 그리고 지금은 **쪽을 잘라 보내는 경우가 많아**(`SEND_PAGES = 12`) 그 경우엔 URL 방식이 안 맞는다. 그래서 효과는 "전체 PDF 보낼 때"로 한정된다.
- 프롬프트 캐시는 이 파이프라인에서 효과가 작다. 프롬프트가 대부분 1,024토큰 미만이고, 앞부분이 기사마다 다르다. 같은 PDF를 2번 읽을 때(`read_pdf` 재시도) **PDF 부분을 앞에, 질문을 뒤에** 두면 두 번째 호출에서 캐시가 걸릴 여지가 있다. Gemini 권고(프롬프트를 쪽 뒤에)와도 맞는다. 다만 게이트웨이 Gemini에서 캐시가 되는지는 문서에 없다.
- Batch는 데모 실시간 경로에는 쓸 수 없다. **평가 세트 재실행(30+19건)이나 미리 데우기**에만 맞는다.
- 병렬 한도: Rerank는 동시 5건이므로 병렬 Rerank는 3~4개로 묶는다. 웹 검색 3개, 다운로드 6개, Chat 2~3개 정도는 동시에 보내도 한도 안이다(추론). 단, 기관 서버(보사연)는 연속 요청에 429를 낸 기록이 있다(`진행현황.md` 18행). 그래서 **기관 도메인별로 동시 2개**를 따로 걸어야 한다.

### Gaps
- 라이너 문서 어디에도 Search·Chat·Rerank의 지연 수치(p50/p90)가 없다. Search Agent의 p50 약 30초만 앞 보고서에 있다. 직접 재야 한다.
- 게이트웨이 경유 Gemini에 `reasoning_effort`가 전달되는지, 게이트웨이 PDF 요청에도 프롬프트 캐시가 걸리는지는 문서에서 확인하지 못했다. 1건 시험 호출로 usage의 `reasoning_tokens`·`cached_tokens`를 보면 된다.
- "계정당 동시 5건"이 일반 Chat에도 걸리는지는 두 문서가 엇갈린다. 동시 6개 Chat을 보내 429가 나는지 시험해야 한다.
- 라이너 Search API에 본문·PDF 텍스트를 돌려주는 옵션은 없다(문서 확인). 그래서 PDF 다운로드 단계를 없앨 방법은 찾지 못했다.

## 동시 실행·투기 실행·조기 종료

### Takeaway
지금 순차인 ②(검색 3번)와 ④(PDF 6개 받기+추출)를 병렬로 바꾸고, "확실히 맞는 쪽을 찾으면 나머지를 버리는" 조기 종료와 Rerank·다운로드 겹치기를 더하면 큰 몫이 빠진다. 표준 라이브러리 `concurrent.futures.ThreadPoolExecutor`로 충분하다. asyncio/httpx로 갈아탈 필요는 없다.

### Cited Findings
- OpenAI 안내는 "엄격히 순차가 아닌 단계는 병렬로", 순차여도 결과를 예측할 수 있으면 **투기 실행(speculative execution)**으로 지연을 숨기라고 권한다. — [OpenAI Latency optimization](https://developers.openai.com/api/docs/guides/latency-optimization)
- OpenFactCheck 벤치마크는 사실 검증 시스템의 지연이 "주로 구현 전략에 달려 있다"고 보고했다. 비동기 처리를 쓰는 FacTool이 Factcheck-GPT보다 빠르다고 적었다. — [OpenFactCheck (arXiv 2405.05583)](https://arxiv.org/pdf/2405.05583)
- 한 개인 블로그(동료 심사 없음)는 LLM 사실 검증 파이프라인에서 근거 검색이 지연의 대부분(주장당 11~29초)이고 LLM 추론 몫은 작았다고 보고했다. — [KEPLER 블로그](https://vineet-loyer-blogs.vercel.app/post/8-kepler)

### Inferences
- **② 검색 3번 동시 실행**: 지금은 3번이 차례로 돈다. 동시에 보내면 검색 단계 시간이 "셋 중 가장 느린 것" 하나로 준다. 작업 30분, 예상 −2~5초(추론).
- **② 와 ① 겹치기(투기 실행)**: 분해 모델을 기다리지 않고 기사 문장 그대로 일반 검색 1번을 먼저 띄운다. 라이너 검색은 자연어 질의를 검색용으로 다시 쓴다([Search API 문서](https://liner.com/developers/docs/search-api)). 기관명이 문장에 보이면(규칙: "자본시장연구원|보건사회연구원|국가데이터처|통계청") site 검색도 바로 띄울 수 있다.
- **④ PDF 받기·추출 병렬**: 후보 6개를 동시에 받고, pdftotext도 프로세스 병렬로 돌린다(기관 도메인당 2개 제한). 6개 순차가 1개 시간 + α로 준다. 작업 1~2시간, 예상 효과는 큼(이번 노트의 최대 후보, 재지 않음).
- **조기 종료**: 다운로드가 끝나는 대로(`as_completed`) 숫자 후보 찾기(`find_candidates`)를 바로 돌린다. 기준시점 일치가 최대이고 숫자·핵심어가 같은 쪽에서 정확히 맞는 PDF가 나오면, 나머지 다운로드를 기다리지 않고 판정으로 넘어간다. 단, 지금의 "Rerank로 표지 순위를 다시 매긴 뒤 상위부터 판정" 순서가 깨지므로 정확도 회귀를 확인해야 한다. 보수적인 대안은 **상위 2개가 끝나면 진행, 나머지는 뒤에서 계속 받아 캐시만**하는 방식이다.
- **⑥ 상위 2개 PDF 판정 동시 실행**: `MAX_DOCS_TO_JUDGE = 2`의 두 `choose` 호출을 동시에 보내고, 순위가 높은 쪽 결과를 우선한다.
- **⑦ 게이트웨이 PDF 읽기 투기 실행**: 글자 찾기 후보가 0곳이거나 숫자가 그림 글자로 감지된 경우에는 ⑥을 기다리지 말고 ⑦을 바로 동시에 시작한다. 2번 시도(일부 쪽 → 전체)도 차례로 하지 말고 **동시에 보내 먼저 맞는 답**을 쓴다. 비용은 늘지만 PDF 쪽당 258토큰이라 적다([Gemini 문서 처리](https://aistudio.google.com/docs/document-processing)).
- **⑧ Decisions 교차 확인은 결과 화면을 먼저 보낸 뒤** 뒤에서 채운다. 판정 자체는 바뀌지 않으므로 기다릴 이유가 없다.
- **asyncio 대신 스레드 풀**: 지금 코드는 `urllib` 동기 호출이고, 사용자 규칙도 "단순한 코드"다. 그래서 `ThreadPoolExecutor(max_workers=6)` + 도메인별 `Semaphore(2)`가 가장 적게 바꾸는 방법이다. httpx를 들이면 연결 재사용(keep-alive)으로 라이너 호출마다 TLS 왕복을 아낄 수 있다. 하지만 이는 의존성을 추가하는 일이라 2순위로 둔다.

### Gaps
- 기관 서버별 동시 접속 허용치는 알 수 없다(보사연 429만 확인됨).
- 조기 종료가 정확도를 얼마나 바꾸는지는 30건 재평가로만 알 수 있다.

## 캐시 층

### Takeaway
PDF 파일 캐시는 이미 있다. 더할 것은 **pdftotext 결과(쪽 목록)**, **검색 결과**, **모델 답(프롬프트 해시)** 세 가지 디스크 캐시다. 데모에서는 "미리 데우기"가 실제 수 초를 만드는 가장 확실한 방법이다.

### Cited Findings
- 라이너 Search API 문서 스스로 `(query, country_code, lang, date_range, include_knowledge)` 기준 캐시를 권한다. — [Search API 문서](https://liner.com/developers/docs/search-api)
- OpenAI 안내는 "Don't default to an LLM" 항목에서 미리 계산한 결과, 하드코딩 응답, 캐시 같은 고전적 방법을 권한다. — [OpenAI Latency optimization](https://developers.openai.com/api/docs/guides/latency-optimization)
- 이 프로젝트에는 PDF 210개가 `작업/원본PDF/`에, 결과 JSON 28개가 `작업/결과/`에 쌓여 있다. — 로컬 확인(`ls`)

### Inferences
- **쪽 텍스트 캐시**: `작업/원본PDF/<이름>.pages.json`처럼 PDF 옆에 pdftotext·PyMuPDF 결과를 저장한다. 큰 PDF는 추출에 수 초가 걸린다(제한 120초를 둔 이유). 작업 30분.
- **검색 캐시**: `작업/캐시/검색/<sha1(query|lang|date_range)>.json`, 유효 하루. 같은 통계 발표를 여러 기사가 인용하므로 적중률이 높다. 날짜가 바뀌면 최신 보도자료가 빠질 수 있다. 그래서 `past_day`·`past_week` 질의는 짧게(1~6시간) 둔다.
- **모델 답 캐시**: `sha1(model + 설정값 + prompt + PDF 해시)` → JSON. 같은 기사 문장을 다시 돌리면(시연 재실행, 평가 재실행) 모델 왕복이 0이 된다. 게이트웨이 PDF 읽기가 "실행마다 흔들리는" 문제(`진행현황.md` 40행)를 고정하는 효과도 있다. 다만 흔들림을 숨기는 것이므로 평가 때는 끌 수 있게 설정값을 둔다.
- **미리 데우기**: 지원 기관 3곳의 최근 보고서·보도자료 목록을 서버를 켤 때 또는 하루 한 번 받아 둔다. 데이터처 '보도자료 전체' 게시판, kcmi 목록, 보사연 목록에서 최근 N개 PDF와 쪽 텍스트를 미리 만든다. 그러면 최근 기사(대부분 최근 보고서 인용)는 다운로드·추출 단계가 사라진다. 더 나아가 **로컬 쪽 텍스트 색인**(숫자 표기 변환 + 핵심어)을 만들면, 검색보다 먼저 로컬에서 "숫자+핵심어가 맞는 쪽"을 찾는 빠른 경로가 생긴다. 이때 라이너 검색은 확인·보충용이 된다. 작업은 반나절~하루다. 단, 라이너 API가 중심이라는 원칙에 맞추려면 이 빠른 경로를 **"라이너 검색과 동시에 출발하는 지름길"**로 설명하고, 판정은 반드시 라이너 모델이 하게 둔다.

### Gaps
- 기사 인용 중 "최근 1~3개월 보고서"가 차지하는 비율을 재지 않아, 미리 데우기의 적중률은 모른다. 기존 평가 49건의 보고서 발간일로 셀 수 있다.

## 모델 나눠 쓰기(라우팅)와 LLM 빼기

### Takeaway
분해·후보 선택처럼 짧은 분류는 **빠른 모델 + 추론 끔**으로 돌린다. 판정이 갈리는 단계만 강한 설정을 쓴다. 분해는 규칙으로 먼저 시도하고 모자랄 때만 모델을 부른다.

### Cited Findings
- 라우터는 `routing_strategy`로 비용·품질 쪽을 고르고, 응답 `model`로 실제 모델을 알려준다. — [GPT Router 문서](https://liner.com/developers/docs/llm-gpt-router)
- 앞 보고서가 이미 "문장 분해는 cost, 최종 판정은 quality"와 "싼 판정자가 자신 있을 때만 답하는 cascade"([arXiv 2407.18370](https://arxiv.org/html/2407.18370v1))를 제안했다. — `reports/원래 어디서 약점 보완 고도화.md` 29·37행
- 지연 안내는 "작은 모델이 일반적으로 더 빠르다"와 "출력 토큰이 지연의 가장 큰 몫"이라고 한다. — [OpenAI Latency optimization](https://developers.openai.com/api/docs/guides/latency-optimization)

### Inferences
- 단계별 권장 설정(시험 전 초안):
  - `extract`(분해): `liner-gpt-router`, `routing_strategy: cost`, `reasoning_effort: none`, `json_schema`, `max_completion_tokens` 300.
  - `rank_hits`/`choose`(후보 고르기+판정): `routing_strategy: balanced`, `reasoning_effort: low`. 30건에서 정확도를 비교해 떨어지면 medium으로 되돌린다.
  - `read_pdf`(게이트웨이): `google/gemini-3.8-flash` + `reasoning_effort: low`. 또는 `google/gemini-3.5-flash-lite`(기본 minimal)로 1차를 보내고, 못 찾을 때만 3.8 Flash를 쓴다.
  - `check_calculation`: 계산 재료 찾기는 규칙(두 숫자의 합·차·비가 기사 숫자와 같은지)으로 먼저 보고, 맞는 조합이 있으면 모델 호출을 건너뛴다.
- **분해와 선택 합치기**: `extract`와 `choose`는 입력이 달라 합칠 수 없다. 하지만 `choose` 다음의 `check_calculation`처럼 같은 쪽을 보는 호출은 하나의 JSON 스키마로 합칠 수 있다(왕복 1번 감소).
- **규칙 분해 먼저**: 숫자(정규식)와 기관명(사전)은 규칙으로 바로 뽑힌다. 그러면 ① 모델 분해를 기다리지 않고 ② 검색을 시작할 수 있다. 핵심어·기준시점은 모델 답이 오면 보충 검색에 쓴다.

### Gaps
- `reasoning_effort` 낮춤이 판정 정확도를 얼마나 떨어뜨리는지 자료가 없다. 반드시 30건 재평가로 확인해야 한다.

## 체감 속도: 단계별로 결과를 먼저 보여 주기 (데모 영상용)

### Takeaway
진짜 속도를 10초 안팎까지 줄여도, 영상에서는 **첫 화면 변화가 1~2초 안에** 일어나는 것이 더 중요하다. 지금의 폴링+`print` 진행 기록을 "단계 이벤트(JSON)"로 바꾼다. 그러면 "기관 찾음 → 보고서 후보 3개 → p.12 숫자 찾음 → 판정"이 차례로 화면에 채워진다.

### Cited Findings
- Nielsen의 응답 시간 한계는 0.1초(즉시), 1초(흐름 유지), 10초(주의 이탈)다. 10초를 넘는 대기에는 진행 표시, 가능하면 '몇 % 완료' 막대를 권한다. — [uxdesign.cc](https://uxdesign.cc/the-waiting-problem-in-ai-products-e7c11fd5a825), [UX Tigers](https://www.uxtigers.com/post/progress-indicators)
- OpenAI 안내는 체감 속도에 스트리밍이 가장 효과적이라 하고, 단계 보이기·로딩 상태도 권한다: "기다리는 것과 진행을 지켜보는 것은 큰 차이가 있다". — [OpenAI Latency optimization](https://developers.openai.com/api/docs/guides/latency-optimization)
- 라이너 Chat Completions는 SSE 스트리밍을 지원한다. 125초 무응답에 끊기는 문제도 스트리밍으로 피한다. — [Chat Completions 문서](https://liner.com/developers/docs/liner-model-api-chat-completions)

### Inferences
- **단계 이벤트**: `run()`에 `emit(단계, 데이터)` 콜백을 넣어 `job["events"]`에 구조화된 값을 쌓는다. 예: `{"단계":"보고서후보","목록":[...]}`, `{"단계":"쪽찾음","쪽":12,"그림":"/page?..."}`. 화면은 지금 폴링(예: 0.5초 간격)으로 이벤트를 그린다. SSE(`text/event-stream`)로 바꿔도 `http.server`에서 가능하지만 폴링으로도 영상 효과는 같다. 작업 반나절.
- **쪽 그림 먼저**: 숫자 후보가 나온 순간 그 쪽의 형광 표시 그림(`page_png`)을 먼저 띄운다. 판정 문장은 나중에 채운다. 사용자가 보는 "원문을 찾았다"는 순간이 판정 완료보다 앞당겨진다.
- **판정 설명 스트리밍**: `choose`의 판정 근거 문장을 `stream: true`로 받아 글자가 흘러나오게 한다. 단, JSON 출력을 스트리밍하면 중간 파싱이 어렵다. 그래서 "판정 JSON 먼저 받고, 사람용 설명만 별도 스트리밍"이 단순하다. 이는 호출이 하나 늘어나는 것이라 우선순위는 낮다.
- **영상에서는 정직하게**: 캐시·미리 데우기로 빨라진 실행이라면 화면에 "캐시 사용" 표시를 둔다. 처음 실행(콜드) 시간도 따로 밝히는 것이 결선 질문("34초·비용")에 안전하다.

### Gaps
- 스트리밍된 AI 출력에 대한 사용자 인내 시간을 직접 잰 통제 연구는 찾지 못했다(위 출처는 고전 UI 연구와 해설 글이다).

## 비슷한 파이프라인의 실제 지연 (비교 기준)

### Takeaway
공개된 근거 기반 사실 검증 파이프라인은 주장당 **약 10~60초**가 보통이고, 검색·근거 수집이 병목이다. "수 초"는 캐시·미리 계산 없이 콜드 상태에서는 업계 사례로도 드물다.

### Cited Findings
- Fathom(FEVER 2025 워크숍, AVeriTeC): 가벼운 오픈소스 RAG 파이프라인으로 주장당 22초 이내. — [FEVER 2025 논문](https://preview.aclanthology.org/evt-to-venues/2025.fever-1.22.pdf) (검색 요약 기준, 원문 수치는 직접 확인하지 못함)
- FEVER 8 공유 과제는 주장당 평균 60초 제한(A10 GPU 1장)을 조건으로 걸었다. — [AIC CTU@FEVER 8 (arXiv 2508.04390)](https://arxiv.org/pdf/2508.04390)
- KEPLER(개인 블로그): 근거 검색이 주장당 11~29초로 지연의 대부분. — [KEPLER 블로그](https://vineet-loyer-blogs.vercel.app/post/8-kepler)
- 라이너 Search Agent 실측 p50 약 30초, p90 약 45초(앞 보고서 인용). — [Search Agent 문서](https://liner.com/developers/docs/search-agent-api)

### Inferences
- 지금 27~41초는 업계 범위 안이고, 라이너 자체 Search Agent(p50 30초)와도 비슷하다. 기획서에는 "같은 일을 사람이 N분 vs 콜드 X초 / 캐시 Y초"로 쓰는 것이 정직하다.
- 현실적인 목표(추론): 콜드 10~15초, 같은 보고서를 인용한 두 번째 기사 3~5초, 데모 첫 화면 변화 1~2초.

### Gaps
- Perplexity 등 상용 서비스의 단계별 지연 공개 자료는 찾지 못했다.
