# 출처 문서 찾기 — 기사 속 통계의 원문 보고서·조항을 정확히 고르는 방법

조사일: 2026-11-13. 검색 약 12회. 아래 [출처] 링크는 실제로 찾아본 것만 적었다. 링크가 없는 내용은 "미확인"으로 표시했다.

## 질문 1. 기사가 보고서 제목을 밝혔을 때 그 보고서를 고르게 하는 순위 신호·규칙은? (참고문헌 매칭 연구 포함)

### Takeaway
학술 참고문헌 매칭(Crossref)에서 가장 좋은 방식은 "검색으로 후보를 넓게 모은 뒤, 별도 검증 단계로 최종 1건을 고르는" 2단계(SBMV)였다. 이 시스템에 적용하면 "기사에 제목이 있으면 제목 일치를 점수가 아니라 관문(hard constraint)으로 쓰는 검증 단계"를 rerank 앞에 두는 것이 된다. 하루 안에 구현할 수 있고, 약점 1을 직접 해결할 것으로 보인다.

### Cited Findings
- Crossref의 참고문헌 매칭 비교(실제 참고문헌 문자열 2,000건과 정답 DOI): 기존 파싱 방식 F1 0.925(P 0.990, R 0.869), 검색 기반(SBM) F1 0.843, **검색 기반 + 검증(SBMV) F1 0.963**(P 0.981, R 0.946). 거짓 양성은 1.05%→1.91%로 조금 늘고, 놓친 비율은 13.15%→5.44%로 줄었다 — [Crossref blog: Reference matching for real this time](https://www.crossref.org/blog/reference-matching-for-real-this-time/)
- SBMV 구조: (1) 참고문헌 문자열 전체로 검색 API를 불러 후보를 받고, 관련도 점수를 문자열 길이로 나눈 값이 임계값을 넘는 것만 남긴다. (2) 별도의 검증 점수로 최종 후보를 고른다. 임계값은 따로 떼어 둔 데이터에서 F1이 가장 높게 나오도록 정했다. 검증에 쓰는 세부 필드·유사도는 블로그에 나오지 않고 Python/Java 구현 저장소를 보라고 되어 있다 — [같은 글](https://www.crossref.org/blog/reference-matching-for-real-this-time/)
- 같은 글에 나온 오류 원인 중 하나는 **"관련 문서와 매칭됨(예: 책의 한 장 대신 책 전체)"**이다. 이번 약점 1(비슷한 주제의 다른 보고서), 약점 2(정기간행물 한 호 vs 그 안의 글 한 편)와 같은 종류다 — [같은 글](https://www.crossref.org/blog/reference-matching-for-real-this-time/)
- 합성 데이터 실험에서는 검색 기반 매칭이 **짧은 문자열, 특히 제목이 빠진 인용 형식**에 약했다. 파싱 방식은 잡음이 많은 문자열에 약했다 — [Crossref blog: Matchmaker, matchmaker, make me a match](https://crossref.org/blog/matchmaker-matchmaker-make-me-a-match)
- RapidFuzz: `fuzz.partial_ratio`는 한 문자열이 다른 문자열의 부분 문자열이면 100을 준다(예: "this is a test" vs "this is a test!" → 100). `token_set_ratio`는 공통 토큰과 고유 토큰을 비교하므로 한쪽이 다른 쪽의 부분집합이면 100이 나온다 — [RapidFuzz GitHub](https://github.com/rapidfuzz/RapidFuzz), [R 바인딩 문서 token_set_ratio](https://rdrr.io/cran/RapidFuzz/man/fuzz_token_set_ratio.html)
- (주의) "partial token set은 공통 토큰이 하나만 있어도 100" 문제는 JS 라이브러리 fuzzball 문서에 나온 설명이다. RapidFuzz에도 그대로 해당하는지는 확인하지 못했다 — [fuzzball](https://socket.dev/npm/package/fuzzball/overview/2.2.6)

### Inferences (이 시스템에 적용할 규칙 제안)
- **제목 관문(1일 이내, 효과 큼)**: LLM이 기사에서 따옴표나 『』로 묶인 보고서 제목을 뽑아 냈다면(`명시제목`), 후보 제목과 **정규화 후 비교**한다. 정규화는 공백·문장부호·「」『』·부제(콜론이나 대시 뒤) 제거, NFC 적용. 아래 중 하나를 만족하면 "제목일치"로 보고 rerank 점수와 관계없이 1순위로 올린다.
  1. 정규화한 문자열이 서로 같다.
  2. 한쪽이 다른 쪽을 포함한다(부제 차이). 단 포함되는 쪽 길이가 상대의 70% 이상일 때만.
  3. 공백을 지운 문자열의 문자 2-gram Jaccard ≥ 0.8 (한국어는 띄어쓰기가 흔들리므로 어절보다 문자 n-gram이 낫다 — 일반론, 논문 근거 미확인).
- 실패 사례에 적용하면: '탄소중립을 위한 기후금융 발전 과제'와 '2050 탄소중립을 위한 자본시장의 변화와 발전 과제'는 포함 관계가 아니다. 2-gram이 일부 겹치지만 '기후금융'이 빠지므로 관문을 통과하지 못한다. 그러면 정답 보고서가 후보에 있을 때만 정답 쪽이 올라간다. 그래서 **정답 보고서가 후보에 들어오게 하는 검색(아래 '제목 우선 검색')이 함께 필요하다.**
- **제목 우선 검색(title-first retrieval)**: `명시제목`이 있으면 첫 검색어를 `"정확한 제목" site:기관도메인`, 그다음 `"정확한 제목" filetype:pdf`로 하고, 기관 사이트 내부 검색(제목 검색)도 부른다. 이 결과를 다른 후보보다 먼저 검증한다. Crossref SBMV의 "문자열 전체로 검색 → 검증" 구조와 같다.
- **부정 신호(hard negative)**: 후보 제목에만 있고 명시제목에는 없는 핵심 명사(예: '1인가구', '자본시장')가 있고, 명시제목의 핵심 명사(예: '소득공백', '기후금융')가 후보 제목에 없으면 감점하거나 탈락시킨다. 약점 1의 두 사례를 모두 막는다.
- **Rerank는 관문 뒤에서만**: Cohere rerank는 주제 유사도를 보므로 "주제는 같고 제목은 다른" 보고서에 높은 점수를 줄 수 있다. 제목이 명시된 경우 rerank는 동점끼리 순서를 정하는 데만 쓰고, 명시제목이 없을 때만 주 신호로 쓴다.
- **임계값은 데이터로 정하기**: Crossref처럼 기존 평가 사례(현재 22/70건 등)에서 F1이 가장 높게 나오는 값으로 정한다. 감으로 정하지 않는다.
- 후보에 정답이 없어 관문을 통과한 후보가 하나도 없을 때는 "명시된 제목의 보고서를 찾지 못함(가장 가까운 후보: …)"으로 보고하는 편이, 다른 보고서를 정답처럼 내놓는 것보다 낫다.

### Gaps
- Crossref SBMV 검증 단계의 세부 필드와 유사도 함수는 블로그에 없다. GitHub 구현은 열어 보지 않았다.
- 한국어 제목 매칭에서 문자 n-gram과 형태소 기반 비교를 비교한 논문은 찾지 못했다.
- Cohere rerank-v3.5에 제목과 본문을 구조화해(YAML 등) 넣을 때 효과가 어떤지는 확인하지 못했다(미확인).
- LLM listwise rerank(예: RankGPT)는 이번에 검색하지 않았다(미확인).

## 질문 2. AVeriTeC·FEVER·QuanTemp 계열 파이프라인은 근거 문서를 어떻게 찾고, 무엇이 검색 성능을 올렸나? (출처 귀속·attribution 연구 포함)

### Takeaway
AVeriTeC 2위 시스템 HerO는 "BM25로 넓게 모으기 → dense 임베딩으로 재정렬"만으로 큰 폭으로 개선됐다(0.187→0.260). LLM이 가상의 팩트체크 문서를 쓰게 하는 HyDE-FC는 추가로 약 +0.02였다. 수치 주장 전용 벤치마크 QuanTemp는 주장을 하위 질문으로 쪼개 검색어로 쓴다. 이 시스템에서는 "가상 문서"보다 "기사 문장에서 하위 검색어 여러 개 만들기(multi-query)"가 싸고 효과가 클 것으로 보인다.

### Cited Findings
- HerO(AVeriTeC 공유과제 2위, AVeriTeC 점수 0.57) — [arXiv 2410.12377](https://arxiv.org/html/2410.12377v2)
  - 검색 구조: BM25로 지식 저장소에서 문장 10,000개를 뽑고, 주장과 생성 문서들의 임베딩 평균(SFR-embedding-2)으로 재정렬해 상위 10개를 고른다.
  - HyDE-FC: LLM이 주장으로부터 가상의 팩트체크 문서를 서로 다르게 8개 만들고(temperature 0.7), 이를 주장에 이어 붙여 검색어로 쓴다.
  - 개발셋 ablation(A 점수): BM25 주장만 0.187 → BM25+dense 재정렬 0.260 → HyDE-FC(Llama-3.1-70b) 0.2801. **재정렬 효과가 +0.073으로 가장 크고, HyDE는 +0.02 정도**였다. 생성기 크기 차이(8b vs 70b)는 거의 영향이 없었다.
- 후속 HerO 2(2025)도 HyDE-FC를 유지하고, 질문을 생성하기 전에 문서를 요약하는 단계(Qwen3 8B)를 넣었다 — 검색 결과 요약 기준, [FEVER 2025 논문 PDF](https://preview.aclanthology.org/acl25-workshop-ingestion/2025.fever-1.16.pdf) (본문은 직접 열어 보지 않음)
- QuanTemp: 팩트체크 기관에서 모은 **수치 주장** 15,514건, 웹 근거 스니펫 423,320개. 근거는 원 주장과 주장 분해로 만든 질문들을 검색엔진에 넣어 모았다. 팩트체크 사이트 결과는 정답 유출을 막으려고 걸러 냈다 — [QuanTemp++ arXiv 2510.22055](https://arxiv.org/html/2510.22055v1)
- QuanTemp++(2025-10)는 원 QuanTemp 근거가 시간 유출(temporal leakage) 때문에 품질이 낮다고 지적한다. 그래서 FCDecomp(팩트체커 작업 방식을 흉내 내 주장을 하위 검색어로 분해)를 제안하고, ClaimDecomp·ProgramFC 같은 분해 방식과 검색 품질(NDCG@10, Recall@10/100, MRR)을 비교했다 — [arXiv 2510.22055](https://arxiv.org/html/2510.22055v1)
- AttributionBench(ACL Findings 2024): "이 근거가 이 주장을 뒷받침하는가" 자동 판정은 fine-tuned GPT-3.5로도 macro-F1 약 80%에 그쳤다. 오류 300여 건을 분석해 보니 **26.8%는 모델이 볼 수 있는 정보와 사람 평가자가 볼 수 있는 정보가 달라서** 생겼고, 모델을 키워도 크게 나아지지 않았다 — [arXiv 2402.15089](https://arxiv.org/abs/2402.15089), [프로젝트 페이지](https://osu-nlp-group.github.io/AttributionBench)

### Inferences
- **다중 검색어(multi-query, 반나절)**: LLM이 검색어를 하나만 만들지 않게 한다. ① 명시제목 그대로, ② 기관 + 핵심 지표명 + 연도, ③ 숫자 + 단위 + 지표명(예: "소득공백 5.4년"), ④ 보도자료 이름(예: "산업활동동향 2026년 9월")을 각각 검색해 합집합 후보를 만든다. QuanTemp의 "원 주장 + 분해 질문" 방식과 같다. 약점 4(KOSIS와 보도자료가 함께 언급된 경우)는 "기사에 언급된 출처를 모두 각각 검색어로 만든다"는 규칙으로 해결할 수 있다. 출처가 둘 이상 언급되면 하나만 고르지 않는다.
- **재정렬 효과가 가장 크다**는 HerO 결과는, 지금 쓰는 Cohere rerank가 방향은 맞음을 보여 준다. 다만 문서 단위(보고서 전체)가 아니라 **쪽·섹션 단위 문단**을 rerank하면 숫자가 든 위치를 더 정확히 찾을 수 있다(추론).
- HyDE는 효과가 작고(+0.02) LLM 호출 비용이 든다. 7일 일정에서는 우선순위가 낮다.
- AttributionBench의 "정보 접근 불일치" 오류는 이 시스템에서 "PDF 일부만 읽고 '원문에 없음'으로 판정"하는 문제와 같은 종류다. 판정하기 전에 숫자가 든 쪽 전체와 표 제목·단위를 함께 넣어야 한다(추론).
- ALCE(인용 생성 벤치마크)는 이번에 직접 확인하지 못했다. 다만 이 과제의 핵심은 생성이 아니라 검색이므로 우선순위가 낮다.

### Gaps
- FEVER 원 과제의 문서 검색(Wikipedia 제목 매칭) 세부 방식은 이번에 따로 확인하지 않았다(미확인).
- Google Fact Check Tools API는 검색하지 않았다. 이 API는 "이미 팩트체크된 주장"을 찾는 도구라서 원문 보고서를 찾는 데는 맞지 않을 것으로 보인다(미확인).
- QuanTemp++의 분해 방식별 검색 수치는 표를 직접 읽지 않아 적지 못했다.

## 질문 3. 한국어 여러 편이 묶인 PDF를 목차·북마크로 나누고, 표를 머리글과 함께 뽑는 도구는?

### Takeaway
1순위는 PyMuPDF `doc.get_toc()`로 북마크를 읽어 글 단위 쪽 범위를 만드는 것이다(반나절). 북마크가 없으면 PDF 앞쪽 목차 쪽의 "제목 … 쪽번호" 줄을 정규식으로 읽고, 그것도 안 되면 큰 글씨 제목(글자 크기 상위)으로 나눈다. 표는 Docling(TableFormer, 텍스트를 PDF 원문 글자에서 가져와 언어와 무관)을 쓰되 무거우므로 "숫자가 발견된 쪽만" 돌린다.

### Cited Findings
- PyMuPDF `get_toc()`는 북마크(outline)를 `[레벨, 제목, 쪽번호]` 목록으로 돌려준다. **북마크가 없는 PDF에서는 빈 목록**을 돌려준다(본문의 목차 글자는 읽지 않는다) — [PyMuPDF tutorial](https://pymupdf.readthedocs.io/en/latest/_sources/tutorial.rst), [StackOverflow 아카이브](https://kiwix.lema.org/stackoverflow.com_en_all_2023-11/questions/64700082/get-table-of-contents-from-a-pdf-with-python)
- 북마크로 나누는 방법: 각 북마크의 쪽부터 다음 북마크 쪽 바로 앞까지를 한 덩어리로 자른다 — [StackOverflow 아카이브](https://kiwix.lema.org/stackoverflow.com_en_all_2023-11/questions/61242817/split-pdf-by-chapters-from-table-of-contents)
- 여러 PDF를 합쳐 만든 파일은 outline 처리에서 IndexError가 날 수 있다 — [관련 글](https://gsdms.csir.co.za/aanews1/pymupdf-indexerror-fix-for-merged) (출처 신뢰도 낮음)
- `split-pdf-by-toc`(PyPI 0.0.3): 북마크로 PDF를 나누는 CLI. 깊이(-d), 제목 필터(-f), 겹침 허용 옵션이 있다. Python 3.12 이상, **AGPL 라이선스**, OCR과 목차 생성은 지원하지 않는다 — [PyPI](https://pypi.org/project/split-pdf-by-toc/)
- Docling: 쪽마다 레이아웃 모델로 제목(section heading)·문단·표·그림을 구분하고, TableFormer로 표의 행·열 구조와 **열 머리글/행 머리글/본문 칸**을 예측한다. 표 글자는 이미지를 다시 읽지 않고 PDF 원래 글자 칸에 맞춰 넣으므로 **언어와 무관**하다. 가벼운 pypdfium 백엔드는 빠르지만 표 복원 품질이 떨어진다 — [Docling Technical Report arXiv 2408.09869](https://arxiv.org/html/2408.09869v5), [Docling 2501.17887](https://arxiv.org/pdf/2501.17887)
- Table Transformer(TATR, Microsoft): 객체 탐지 기반으로 표 위치와 구조를 찾는다. **글자는 직접 읽지 않으므로** PDF 글자나 OCR을 따로 넣어야 HTML/CSV를 만들 수 있다. PubTables-1M과 FinTabNet으로 학습한 v1.1 가중치가 있다 — [GitHub microsoft/table-transformer](https://github.com/microsoft/table-transformer), [CVPR 2022 논문](https://openaccess.thecvf.com/content/CVPR2022/html/Smock_PubTables-1M_Towards_Comprehensive_Table_Extraction_From_Unstructured_Documents_CVPR_2022_paper.html)
- marker(datalab-to/marker, 옛 VikParuchuri/marker): PDF를 Markdown/JSON/HTML로 바꾸고 표를 서식화한다. surya로 레이아웃과 읽기 순서를 잡는다. `pip install marker-pdf`, GPU 권장, **GPL-3.0** — [GitHub](https://github.com/VikParuchuri/marker)

### Inferences (보건복지포럼 같은 정기간행물 나누기 절차, 1일)
1. `doc.get_toc()` 결과가 있으면 레벨 1(또는 2) 항목으로 쪽 범위를 만든다. 각 덩어리에 `{글제목, 시작쪽, 끝쪽}`을 붙인다.
2. 북마크가 없으면 앞 1~4쪽에서 목차 줄을 찾는다(정규식 예: `^(.+?)\s*[·\.…]{2,}\s*(\d{1,3})$` 또는 "제목 + 공백 + 쪽번호"). 인쇄 쪽번호와 PDF 쪽번호가 다르므로, 첫 글 제목이 실제로 나오는 PDF 쪽을 찾아 차이(offset)를 보정한다.
3. 그래도 안 되면 `page.get_text("dict")`의 span 글자 크기를 보고 그 호에서 가장 큰 글씨 줄이 있는 쪽을 "글 시작 쪽"으로 본다(필자명·소속 줄이 바로 뒤에 붙는 경우가 많음 — 실제 PDF로 확인 필요).
4. 숫자를 맞춰 볼 때 **덩어리별로** pdftotext 결과를 따로 만들고, 결과에 "○○호 중 '글제목'(xx~yy쪽)"을 적는다. 기사의 명시제목이 호 제목이 아니라 글 제목과 같으면 그 덩어리만 본다. 약점 1과 2를 함께 해결한다.
5. 표: 숫자가 발견된 쪽만 Docling으로 변환해 표 머리글(열/행)과 단위를 함께 LLM에 넘긴다. 전 쪽 변환은 느리므로 피한다.
- 라이선스: split-pdf-by-toc(AGPL)와 marker(GPL)는 공모전 제출물에 넣을 때 라이선스를 확인해야 한다. PyMuPDF도 AGPL(또는 상용)이다 — PyMuPDF 라이선스는 이번에 확인하지 않음(미확인, 일반 지식).

### Gaps
- Docling이나 marker로 한국어 PDF의 제목과 표를 뽑았을 때의 정확도 자료는 찾지 못했다. 실제 보건복지포럼·KCMI PDF 2~3개로 직접 시험해야 한다.
- 보건복지포럼·KCMI 이슈보고서 PDF에 북마크가 실제로 들어 있는지는 확인하지 않았다(미확인, 직접 `get_toc()`로 확인 필요).
- GROBID(학술 논문 PDF → TEI XML)는 이번에 검색하지 않았다. 학술지 논문 출처(약점 3)를 다룰 때 참고할 만하다(미확인).
- Unstructured 라이브러리는 확인하지 못했다.

## 질문 4. 뉴스 속 인용 출처의 "종류"(보고서·통계표·학술논문·의원실 자료 등)를 분류한 연구가 있나?

### Takeaway
뉴스 출처 귀속(누가·무엇이 정보를 줬나)을 다룬 데이터셋은 있지만, "통계 수치의 출처 종류"만 분류한 데이터셋은 찾지 못했다. 이 시스템에서는 LLM 추출 단계에 `출처종류` 필드(보고서/보도자료/통계표(KOSIS)/학술논문/국회의원실 자료/자체 분석·마이크로데이터/기타)를 추가하고, 종류별로 다른 검색 경로와 결론 문구를 쓰는 규칙 방식이 현실적이다.

### Cited Findings
- Spangher 외(EMNLP 2023) "Identifying Informational Sources in News Articles": 뉴스 기사 1,304건에서 출처 귀속 약 28,000건을 모아, 16개 범주의 출처 분류 체계로 주석을 달았다. fine-tuned GPT-3의 귀속 정확도는 83%였다. 범주 이름 목록은 초록 페이지에 없어 확인하지 못했다 — [arXiv 2305.14904](https://arxiv.org/abs/2305.14904v1)
- MacLaughlin 외(ICWSM 2020): 건강·과학 뉴스 뒤에 있는 보도자료를 찾아 연결하는 연구. 과학 저널리즘 교수 2명과 함께 0~3 척도로 문장을 표시했다 — [논문 PDF](https://khoury.northeastern.edu/home/dasmith/maclaughlin-icwsm-2020.pdf)
- Newell 외(IJCNLP 2017) "Assessing the Verifiability of Attributions in News Text": 뉴스 속 출처 표시를 실제로 검증할 수 있는 정도를 점수로 매기는 연구 — [ACL Anthology I17-1076](https://preview.aclanthology.org/setup/I17-1076)
- Scrutinizer(VLDB 2020): 통계 주장을 관계형 데이터에 대한 SQL 질의로 바꿔 검증하도록 팩트체커를 돕는 시스템. IEA 팩트체커 대상 실험에서 정확도를 떨어뜨리지 않고 검증 시간을 크게 줄였다. 관련 연구로 AggChecker(SIGMOD 2019)가 있다 — [arXiv 2003.06708](https://arxiv.org/pdf/2003.06708), [DOI](https://doi.org/10.14778/3415478.3415520)

### Inferences
- **출처종류 분류(반나절)**: 기사 문장의 단서어로 1차 분류하고, LLM이 확정한다.
  - 학술논문: "학회지", "논문", "게재", "저널", 학술지명 → "학술지 논문으로 보임, 보고서 검색 범위 밖"으로 표시하고, 가능하면 KCI/RISS 검색 링크를 준다.
  - 의원실 자료: "○○○ 의원실", "의원이 ○○부로부터 제출받은 자료" → "국회의원실이 받은 비공개 제출 자료로, 공개 원문이 없을 수 있음".
  - 자체 분석: "원자료를 분석", "마이크로데이터", "○○ 분석 결과(기관 아닌 언론사·연구자)" → "원자료를 직접 분석한 결과라 같은 숫자가 담긴 공개 문서가 없을 수 있음".
  - 통계표: "KOSIS", "국가통계포털", "통계표" → KOSIS 표 검색 경로로 보낸다. 단 **보도자료 이름이 같이 나오면 보도자료도 반드시 검색**한다(약점 4).
  - 보고서/보도자료: 지금의 기본 경로.
- 결론 문구를 "원문에 없음" 하나로 두지 말고 "출처 종류가 ○○라 공개 원문을 찾을 수 없음" / "찾은 문서에 숫자 없음" / "후보 문서를 찾지 못함"으로 나누면, 평가에서 오답이 아니라 정당한 판정으로 보일 수 있다(추론).
- Scrutinizer 방식(주장 → SQL)은 KOSIS 표 숫자 대조에 개념적으로 맞지만, 7일 안에 구현하기는 어렵다. KOSIS는 "표 ID 찾기 + Open API 값 조회 + 숫자 비교"까지만 하는 것이 현실적이다(추론, KOSIS API 세부는 미확인).

### Gaps
- Spangher 외의 16개 출처 범주 이름은 논문 본문을 열지 못해 확인하지 못했다.
- 한국어 뉴스에서 통계 출처 종류를 분류한 연구·데이터셋은 찾지 못했다.
- 언론사(예: 데이터저널리즘 팀)가 통계 출처를 관리하는 실무 블로그 글은 찾지 못했다.
